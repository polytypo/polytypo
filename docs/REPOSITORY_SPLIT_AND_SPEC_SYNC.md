# Repository split and spec-sync automation

Status: **design only. Nothing in this document has been executed.** No repository was created, no
history was rewritten, no file was moved, no workflow that can mutate an external system was added,
and the split has not happened. This document is Stage 9 of `docs/AUDIT_REMEDIATION_AND_RELEASE_PLAN.md`
§8 — an implementation-ready plan, executable after Stage 10 (final release audit) and after the
JavaScript implementation clears the M4 dogfooding gate (`docs/ROADMAP.md` M4 and
`docs/AUDIT_REMEDIATION_AND_RELEASE_PLAN.md` §8.6).

The chosen repository model, binding for this document and reconciled with `docs/ARCHITECTURE.md`
and `docs/ROADMAP.md`:

- `github.com/polytypo/polytypo` — canonical: spec, fixtures, schemas, citations, shared docs,
  brand, public site, conformance coordination.
- `github.com/polytypo/polytypo-js` — native JavaScript implementation, npm package `polytypo`.
- Future, **not created now**: `github.com/polytypo/polytypo-python`, `polytypo-go`,
  `polytypo-ruby`, `polytypo-php`.
- Spec transport to every runtime repository: an automated, vendored, content-hashed snapshot
  (§3), not a git submodule and not a consumer-time git dependency.

`docs/ARCHITECTURE.md` and `docs/ROADMAP.md` use the same repository names and the same
vendored-snapshot spec-transport decision as this document; §14 states the exact relationship among
all three, and the audit plan.

### 1.3 Ambiguous ownership, resolved

Three real coupling points exist today where JavaScript-specific code reaches directly into `src/`.
Each is resolved as a concrete design decision. **None of the three resolutions may be treated as
optional or deferred to "sometime after the split" — §2 makes them a precondition of cutting
`src/` out of canonical at all, not a follow-up task.**

**(a) `brand/tools/gen_examples.ts`** imports `transform` from `../../src/index.js` (line 9) to
generate every example string in `promo/examples.json`, which `build_promo.py` renders and
`README.md`/`docs/ports/*.md` quote. This is the site-generation pipeline reaching across the
future repository boundary. **This is the current, factual state — the site does not yet run a
published package for this purpose.**

*Resolution:* canonical's site-generation tooling must depend on the published `polytypo` npm
package as an ordinary devDependency of `brand/tools/`'s own (new, canonical-local) `package.json`
— the same way any third-party consumer would depend on it. `gen_examples.ts`'s import changes from
`../../src/index.js` to `polytypo`. This is not a workaround; it is the intended end state: the
public site must only ever demonstrate what is actually published, never implementation internals a
consumer cannot reach. §2 makes "this switch is made and proven equivalent" a precondition of the
split, not a post-split cleanup task — see §2.2 and §2.10.

**(b) `promo/vendor/polytypo.browser.js`** is generated by `npm run gen:promo-bundle`
(`esbuild src/index.ts --bundle ...`) — today the playground's in-browser engine is bundled
directly from `src/`, **not** from the published package, and no claim anywhere in this document
should be read as saying otherwise about the current state.

*Resolution:* same as (a) — canonical's `gen:promo-bundle` equivalent must run `esbuild` against the
installed `polytypo` package's entry point (`node_modules/polytypo/dist/index.js`), not a sibling
repository's `src/`. The playground then runs exactly the published artifact.

**(c) `tests/promo/proof-grid.test.ts`** imports `transform` from `../../src/index.js` (line 23) to
assert the generated proof-grid output matches a fresh call to the real engine.

*Resolution:* same import-source change as (a): `../../src/index.js` becomes `polytypo`. The test's
intent (cross-check every generated string against the live engine, never trust a cached value
blindly) is unchanged — only which engine build counts as "live" changes, from a sibling directory
to an installed package.

**(d) `scripts/validate-spec.mjs` → `scripts/lib/is-letter.mjs` → `src/engine/letter-ranges.json`** —
`is-letter.mjs`'s own comment explains it re-parses `src/engine/letter-ranges.json` directly
(instead of importing `src/engine/unicode.ts`) because Node has no native TypeScript support.
Canonical's spec validator depends on a JS-engine-internal data file.

*Resolution — flagged for an explicit operator decision (§12), not decided here, because it changes
what `spec/` contains.* Two candidates:

1. **Duplicate.** Canonical gets its own small, self-contained copy of `is-letter.mjs` +
   `letter-ranges.json`. Cheapest, but is a second place the same Unicode-category boundaries must
   stay in sync.
2. **Promote `letter-ranges.json` to `spec/`** as canonical, version-pinned Unicode reference data
   — consistent with `docs/MULTILINGUAL_ARCHITECTURE.md`'s "Unicode Foundation" section: "All
   runtimes must generate equivalent tables from the Unicode version pinned in `spec/UNICODE`."
   Every runtime, including JS, then generates its own internal representation from the canonical
   file, the same way locale JSON is vendored and then embedded. Architecturally cleaner, but is a
   `spec/` surface-area change and needs the same data-plus-citation rigor `AGENTS.md` already
   requires for locale data.

Recommendation: (2) is more correct long-term and `spec/UNICODE` already exists for exactly this
purpose; (1) is a same-day mechanical fix if the split needs to happen before a proper review of
that surface-area change can be scheduled. Pick one before the split.

### 1.5 Generated independently in both repositories

Not literal shared files — shared patterns, each repository implementing its own instance:

- **Embedded-data codegen.** JS: `scripts/gen-locales.mjs` → `src/generated/locales.ts`. Every
  future runtime needs the equivalent step in its own idiom (Python: build-time codegen into a
  package data payload; Go: `//go:embed` over vendored JSON directly; etc.). The policy — "embed at
  build time, never read `spec/` at runtime" — is canonical (`docs/ARCHITECTURE.md` §4); the tool is
  runtime-specific.
- **Generated-artifact drift check.** JS CI regenerates then `git diff --exit-code`s its own
  generated files; canonical's CI does the equivalent for `README.md`/`docs/ports`/`promo/*` after
  the split.
- **Conformance running.** §1.2 above: each runtime writes its own runner against the vendored
  fixtures.
- **Unicode table generation**, if §1.3(d) resolves toward option 2: each runtime derives its own
  internal representation from the one canonical, version-pinned source file.

## 2. Migration sequence and history preservation

### 2.1 Precondition: a real JS release must exist before the split — otherwise NO-GO

This is a hard prerequisite, not an accepted gap to work around later. Canonical's own
site-generation tooling (§1.3a/b/c) has no supported way to run against a real, published engine
until one has been published. Concretely, before the split:

1. `polytypo-js`'s first real npm release exists, is tagged, and has passed the full release gate
   in `.github/workflows/release.yml` (validate-spec, lint, typecheck, test, build, packed-tarball
   checks, package-content assertions, entry-reach, bundle-size, provenance-verified publish).
2. Canonical's site-generation tooling (`gen_examples.ts`, `gen:promo-bundle`, `proof-grid.test.ts`)
   is switched from `../../src/index.js` to the exact published version of `polytypo`, pinned as a
   devDependency (never a floating range, never a consumer-time git dependency of any kind — a
   `package.json` `"polytypo": "1.0.0"` exact pin or npm's lockfile-pinned equivalent).
3. Package-generated examples and the browser bundle built from the installed published package are
   proven behavior-equivalent to the pre-cutover, `src/`-built versions, using §2.10's checklist,
   before the local copy of `src/` is deleted from canonical.
4. Only once 1–3 are all true does deleting `src/` from canonical's continuing history become safe.

**If step 1 has not happened, the split is NO-GO.** This is restated as a hard gate in §13.

### 2.2 Chosen approach

Keep the current repository as `polytypo` (canonical) in place — its `package.json`
`repository.url` already points at `github.com/polytypo/polytypo`, and its issue tracker and any
existing stars/watchers stay attached to the right name. Produce `polytypo-js` as a
history-aware filtered clone of the current repository, keeping only the paths that belong to it
(§1.2, §1.8), using `git filter-repo` — the tool GitHub's own migration guidance points to over the
deprecated `git filter-branch`, and the tool most suited to selectively keeping a path list while
rewriting paths in one pass. The current tree is already close to the target split (JS code, tests,
and tooling are already segregated from `spec/`/`brand/`/`promo/` almost everywhere except the
three coupling points in §1.3a–c), so a filtered clone is simpler than a fresh-history import and
preserves real commit authorship and dates.

### 2.3 Freeze point and prerequisites

- §2.1's precondition is satisfied.
- All planned pre-split work is merged to the trunk branch used as canonical history (`master`, per
  the current repository).
- `npm test`, `npm run build`, `npm run validate:spec`, and `npm run generate:all` all pass with a
  clean, zero-diff working tree on the exact commit chosen as the freeze point.
- No open PR touches `spec/`, `src/`, `brand/tools/`, `scripts/`, `.github/workflows/`, or
  `package.json` at once (§2.9 covers what to do if one exists at cutover time).
- The operator has decided every item this document flags but does not decide unilaterally:
  §1.3(d)'s Unicode-data ownership, and any remaining naming or scope question raised in §12.
- `git filter-repo` is installed (`pip install git-filter-repo` or the OS package) by whoever
  executes the migration; not a prerequisite this document itself satisfies.

### 2.4 Clean-worktree requirement

`git status` must show no staged or unstaged changes and no untracked files the operator wants kept,
on the exact freeze commit, in both the working copy that continues as `polytypo`'s history and the
working copy that gets filtered into `polytypo-js`'s new history. A dirty tree at filter time risks
the filter step operating on working-copy state instead of the intended commit.

### 2.5 Backup and recovery points

Before any history-rewriting command runs (none are part of this design's own scope):

1. `git bundle create polytypo-freeze.bundle --all` from the canonical repository — a complete,
   restorable snapshot independent of the GitHub remote.
2. Tag the freeze commit locally: `git tag pre-split-freeze <sha>` — not pushed until the operator
   confirms the split is final.
3. Keep the bundle and a `git clone --mirror` of the pre-filter state until `polytypo-js` has been
   live, green, and dogfooded for at least one full release cycle post-split.

### 2.6 Exact ref, tag, and release inventory — captured at freeze, not assumed now

As of 2026-08-27, `git for-each-ref` on this repository returns exactly two refs: `refs/heads/master`
and one non-branch, non-tag ref, `refs/codex/turn-diffs/checkpoints/<hash>/<hash>/<timestamp>/<uuid>`
— an automated tooling checkpoint, not a branch a human created. `git tag --list` returns nothing;
`package.json`'s version is `0.0.0`; no release has shipped. **This is an inventory observation
dated 2026-08-27, not a migration assumption.** It must be rechecked at the actual freeze point,
because by the time §2.1's precondition is satisfied (a real npm release has shipped), at least one
release tag will exist and must be preserved, and other branches or checkpoint refs may exist that
did not exist on this date.

At freeze time, the operator must run, and act on the actual output rather than this document's
snapshot of it:

```bash
git for-each-ref --format='%(refname) %(objecttype) %(objectname)'
git branch --all
git tag --list
```

Every ref returned must be individually classified — kept as-is on canonical, included in the
filtered JS history, or explicitly excluded with a reason — never discarded by default because
`master` happens to be the only *branch* visible today. In particular: any `v*` release tag
(§2.1 will have produced at least one) must be preserved in the filtered `polytypo-js` history,
since it touches `package.json` and other kept paths and therefore survives `git filter-repo`'s
normal behavior without special handling; any intentionally-created maintenance branch found at
freeze time must be filtered the same way as `master`, not dropped; and any tooling-internal
checkpoint ref of the kind observed today should be investigated (what created it, is it still
referenced by anything) before deciding whether it needs to survive the filter at all — it is very
unlikely to belong in either target repository's history, but "unlikely" is not the same as
"confirmed," and this document does not confirm it.

### 2.7 Commands to create the filtered JS history

Illustrative, not executed. Run from a disposable clone, never the operator's working copy. The
`--refs` list must be built from §2.6's actual freeze-time enumeration, not copied verbatim from
this example:

```bash
# 1. Disposable clone, never the real working copy.
git clone --no-local /path/to/polytypo polytypo-js-filtered
cd polytypo-js-filtered

# 2. Restrict to the refs decided in §2.6 (illustrative — replace with the actual freeze-time list,
#    which must include master and every preserved release tag/maintenance branch).
#    git filter-repo --refs master --refs 'refs/tags/v*' ...

# 3. Keep only JS-runtime-only and ambiguous-resolved-to-JS paths (--path keeps everything under
#    the given path and drops the rest; repeat --path per §1.2/§1.8).
git filter-repo \
  --path src/ \
  --path tests/rules/ --path tests/engine/ --path tests/modes/ \
  --path tests/conformance/ --path tests/packaging/ --path tests/scripts/ \
```

### 2.8 Releases, issues, discussions, GitHub Pages

- **GitHub Releases:** attached to tags on a specific repository, not portable by any `git` history
  command. Any that exist by freeze time (§2.1 guarantees at least one) must be manually re-created
  on `polytypo-js` pointing at the corresponding filtered-history commit, or left on `polytypo` with
  a note that they describe pre-split monorepo state. Manual work, flagged in §12.
- **Issues:** GitHub supports transferring an open issue between repositories owned by the same
  user or organization, retaining its comments and assignees, and retaining labels/milestones that
  match by name (and, for milestones, by name and due date) in the destination repository. Transfer
  requires write access to both repositories, and a private-repository issue cannot be transferred
  to a public repository. Given that, triage individually rather than bulk-migrating: canonical/spec
  /site issues stay on `polytypo`; clearly JS-implementation-only open issues may be transferred to
  `polytypo-js` once it exists; issues that are mixed (a typography question plus an implementation
  bug) stay on `polytypo` and get a linked companion issue opened on `polytypo-js` for the
  implementation half, rather than being transferred whole. GitHub's issue transfer preserves
  comments and assignees, and is available for this use — nothing here depends on comments being
  lost or on transfer being unsupported.
- **Discussions:** GitHub Discussions have no first-class cross-repository transfer feature; if any
  exist at freeze time, they stay on `polytypo` and are linked from `polytypo-js`'s README if
  relevant, not migrated.
- **GitHub Pages:** not configured yet (§7 — hosting is prepared, not deployed, in this document).
  Nothing to migrate.

- From `polytypo-js`'s filtered history: nothing needs removing — §2.7's filter step already
  excludes `spec/`, `brand/`, `promo/`, `docs/` from that history entirely.
- From `polytypo` (canonical, continuing in place): `src/`, `tests/rules/engine/modes/conformance/

### 2.10 Open PRs

Any PR open against the pre-split repository at cutover time must be triaged before the filter
step, not after: a PR touching only canonical-scope paths (§1.1/§1.4) is merged or closed before
filtering, since `polytypo` continues in place unaffected. A PR touching only JS-scope paths (§1.2)
is handled the same way, so the filtered history includes it. A PR touching both (realistically,
only one of the §1.3 coupling points) must be split into two PRs against the two future
repositories, which is only possible once `polytypo-js` exists — do not filter history while any
cross-cutting PR is open; close the gap first.

### 2.11 Rollback procedure

**Before remote cutover** (before `polytypo-js` is pushed to GitHub as a real, public repository):
the filtered clone is a disposable local directory; delete it and start over. Canonical `polytypo`
was never touched by the filter step, so there is nothing to roll back there.

**After remote cutover:** repository creation and initial push are not silently reversible in the
sense of "as if it never happened," but the technical rollback is: keep `polytypo-js` unpublished to
npm (no tag pushed, §2.5's backup tag stays local-only) until §2.10's equivalence checklist is fully
green; if it fails, the GitHub repository can be deleted or archived and the split re-attempted from
the `pre-split-freeze` bundle (§2.5) without any data having left `polytypo`, since canonical's own
history and content are never rewritten by this migration — only copied-and-filtered into a new
repository.

## 3. Vendored spec snapshot contract

### 3.1 Layout

```text
vendor/polytypo-spec/
```

### 3.2 Canonical source inventory — automatic, not a hardcoded allow-list

The inventory is defined **structurally**, not as a fixed list of six paths that must be edited by
hand every time a legitimate new canonical file appears:

> The inventory is every regular file (a normal git blob — never a symlink, submodule/gitlink, or
> any other non-regular tree entry) reachable under the tagged commit's `spec/` tree, **except**
> paths under any directory explicitly documented as a generated mirror — today, only
> `spec/fixtures/.escaped/`. A new rule file, a new locale file, a new fixture file, or a new schema
> file that lands under `spec/` in a normal, reviewed commit is automatically part of the next
> snapshot's inventory without any change to the snapshot tooling itself. Removing this automatic
> inclusion (hardcoding a path list again) would silently stop protecting new canonical files the
> moment they're added — exactly the failure this design avoids.

### 3.3 Manifest schema (`manifest.json`)

```json
{
  "manifestVersion": "1.0.0",
  "specVersion": "0.4.0",
  "canonicalTag": "spec-v0.4.0",
  "canonicalCommit": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2",
  "contentHash": "sha256:6be8a405b3dae495af7ad8ab3d710840b499c50abefd8421ad0b42a2e3ef9627",
  "canonicalSourceUrl": "https://github.com/polytypo/polytypo/tree/spec-v0.4.0/spec",
  "generatedFileWarning": "This directory is generated by scripts/update-spec.mjs from a tagged canonical snapshot. Do not hand-edit any file under vendor/polytypo-spec/ — edits are silently discarded on the next spec sync and are never reflected in the canonical spec repository.",
  "files": [
    {
      "path": "VERSION",
      "length": 5,
      "sha256": "cd78534ed15ad46912b71339d1417d0d043d8309c2b94415f3ed1b9d1fdfaed0"
    },
    {
      "path": "locales/en-US.json",
      "length": 16,
      "sha256": "329d480ffec2d80a0c884cdf97c660dc5131b4a49f6fabc7cdbfa810a0e99217"
    },
    {
      "path": "rules/quotes.md",
      "length": 27,

    }
  ]

```

The three files and their exact byte content shown as `files[]` entries above (`VERSION` = `0.4.0`,
`locales/en-US.json` = `{"code":"en-US"}`, `rules/quotes.md` = `# Quotes\n\nNormative prose.\n`)
were hashed and the `contentHash` above was computed from them using the exact algorithm in §3.5, so
this is a genuine, checkable worked example, not an illustrative placeholder — it is a three-file
excerpt standing in for the full ~50-file real inventory, not what a real snapshot's `files[]` array
looks like in full.

Field notes:

- `manifestVersion` — the manifest's own schema version, independent of `specVersion`, so the
  manifest format can evolve without conflating "the manifest schema changed" with "the typography
  spec changed."
- `specVersion` — copied verbatim from canonical `spec/VERSION` at snapshot time.
- `canonicalTag` / `canonicalCommit` — the exact `spec-vX.Y.Z` tag and the full 40-character SHA it
  pointed at when the snapshot was cut, recorded even though tags are meant to be immutable, because
  a tag can be force-moved and the SHA is the unambiguous reference each runtime verifies against
  (§4 step 5).
- `contentHash` — the single aggregate hash (§3.5) over the entire authenticated `files[]`
  inventory. Independent of both `canonicalTag` and `canonicalCommit`, so a runtime — or a human —
  can confirm "these files are identical to some known-good snapshot" without trusting either
  string.
- `files` — the authenticated per-file inventory (§3.4). This is what makes the snapshot
  tamper-evident against *missing or additional* files, not just modified ones: an aggregate hash
  alone cannot distinguish "one file changed" from "one file was silently added or removed" without
  an inventory to check membership against.
- `canonicalSourceUrl` — human-clickable provenance link, not machine-verified (URLs can 404
  without invalidating the snapshot; the hash is the machine-verified fact).
- `generatedFileWarning` — literal text embedded in the manifest itself, so a tool or person
  inspecting `manifest.json` alone sees the warning without needing directory context. No timestamp
  field anywhere in this manifest — `canonicalCommit` and `canonicalTag` already give unambiguous
  provenance without a clock, and a timestamp would make the manifest, and therefore the hash,
  non-deterministic across otherwise-identical snapshot runs.

`manifest.json` is excluded from its own `files[]` list and from its own `contentHash` — it cannot
authenticate itself before it exists, and `contentHash` is computed before `manifest.json` is
written, never the reverse.

### 3.4 Path and entry validation rules

Applied when building the inventory (canonical side) and when verifying a received snapshot
(runtime side) — the same rules, both directions:

- Every `files[].path` is a normalized, UTF-8, forward-slash relative path from
  `vendor/polytypo-spec/` (e.g. `rules/quotes.md`), with no leading `./`, no trailing slash.
- Paths must be **unique** — a manifest containing the same `path` twice is invalid and must be
  rejected before any hash is even computed.
- **Rejected outright, both when building and when verifying:** an absolute path; any path segment
  equal to `..`; any empty path segment (e.g. `a//b`); any backslash character (`\`) anywhere in the
  path (this project targets POSIX-style relative paths only — a backslash is either a
  Windows-path-separator confusion or an attempted escape, never legitimate); any NUL (`\0`) or line
  feed (`\n`) byte in the path (both would make the path ambiguous or dangerous to store as a plain
  text/JSON string and as a length-prefixed binary record); a symlink; a git submodule / gitlink
  entry; or any tree entry that is not a regular file.
- **No file may exist inside `vendor/polytypo-spec/` on disk while being absent from `files[]`.**
  Verification (§3.6) walks the actual snapshot directory independently of the manifest and treats
  any file present on disk but not listed in `files[]` as a hard failure (an "extra file"), exactly
  like walking the manifest and finding a listed file missing from disk is a hard failure (a
  "missing file"). The inventory and the on-disk snapshot must match exactly in both directions.

### 3.5 Content-hash algorithm

Precise enough for independent, correct implementations in JS, Python, Go, Ruby, and PHP with no
`git` installation required at consumer (runtime-repo CI) time, and precise enough to be
unambiguous — not just "hard to collide by accident," but structurally incapable of two different
file sets producing the same aggregate hash through a framing mistake.

1. **Included files.** Every entry in `manifest.json`'s `files[]` array (§3.2, §3.4) — nothing more,
   nothing less. The set of included files is *defined by* `files[]`, and `files[]` is *defined by*
   the structural rule in §3.2; there is no separate, independent "what gets hashed" list to keep in
   sync.
2. **Ordering.** Files are processed in ascending order of `path`, compared as raw UTF-8 bytes
   (ordinal/byte-wise comparison, never a locale-aware sort — consistent with `AGENTS.md`'s "No
   locale-dependent stdlib calls" rule, applied here to tooling rather than rule code, for the same
   reason: a locale-aware sort order is not guaranteed identical across the five target languages'
   standard libraries, and a byte-wise sort is).
3. **Per-file digest.** For each file, compute `SHA-256(raw file bytes)` — the file's literal
   on-disk bytes at the tagged commit, with **no** line-ending normalization, **no**
   re-serialization of JSON (never parse-and-reprint; hash the file's literal bytes), and no BOM
   handling beyond whatever the canonical files already do or don't contain. This value is stored as
   64 lowercase hex characters in `files[].sha256`.
4. **Aggregate framing.** Build one binary byte stream by concatenating, for each file in sorted
   order, exactly these four fields with no separator characters between or within them:
   - the file's normalized relative path, UTF-8 encoded;
   - preceded by an 8-byte big-endian unsigned integer giving that path's UTF-8 byte length;
   - the file's raw SHA-256 digest — the **raw 32 bytes**, not the hex string — from step 3;
   - preceded by an 8-byte big-endian unsigned integer giving the file's raw content byte length
     (from `files[].length`).

   In other words, each file's record is
   `u64be(len(path_utf8)) || path_utf8 || u64be(content_length) || sha256_digest_raw_32_bytes`,
   and the full stream is those records concatenated in sorted order with **no** additional
   separators, since every field is already self-delimited by an explicit length prefix. This is
   what makes the framing collision-proof against the classic ambiguity a plain separator or a
   bare-concatenation scheme has: without explicit lengths, the byte streams `"ab"+"cd"`
   (path `"ab"`, content `"cd"`) and `"a"+"bcd"` (path `"a"`, content `"bcd"`) are **both**
   literally `abcd` — indistinguishable — even though they describe two completely different file
   sets. With the length-prefixed framing above, those two file sets produce different aggregate
   hashes by construction, because the length fields make the split point between "path" and
   "content" (and between one record and the next) unambiguous no matter what bytes either field
   contains. §3.7 gives the actual computed digests proving this.
5. **Aggregate hash.** `SHA-256` over the single concatenated byte stream from step 4. Hex-encoded,
   lowercase, prefixed `sha256:` in the manifest (§3.3). SHA-256 is chosen because it has a
   standard-library or trivially available implementation in all five target languages with no
   external dependency.
6. **Symlinks and unexpected entries.** Already covered structurally by §3.4 (rejected at inventory
   time, not silently skipped or silently included) — repeated here because it is also a hashing
   concern: a symlink's "content" is ambiguous (target path vs. resolved target's content), so the
   algorithm never defines a behavior for hashing one; it must never reach step 3 at all.

A reference implementation of this exact algorithm belongs in `scripts/lib/spec-content-hash.mjs`
in the canonical repository (§1.8), used by whatever tool cuts the `spec-vX.Y.Z` tag (§4), so every
runtime's independent reimplementation has one authoritative, testable oracle to check against —
the same discipline this project already applies to typography rules, extended to the hash
algorithm itself. **Every runtime's reimplementation must pass the exact test vectors in §3.7**
before its `spec-update.yml` (§4) is trusted to verify a real snapshot.

### 3.6 Runtime verification failure modes

A receiving runtime, on every spec sync, must fail (not warn, not proceed with a partial update) on
any of:

- a file listed in `manifest.json`'s `files[]` that is missing from the downloaded snapshot;
- a file present in the downloaded snapshot that is not listed in `files[]`;
- a duplicate `path` within `files[]`;
- a file whose actual byte length does not match its `files[].length`;
- a file whose actual `SHA-256(content)` does not match its `files[].sha256`;
- a recomputed aggregate hash (§3.5) that does not match `manifest.json`'s `contentHash`.

Any one of these failing means the entire snapshot is rejected — no partial update, no "apply the
files that did match." §4.1 (steps 8–9) covers what a receiving workflow does with this failure
(fail loudly, no PR is opened for an unverified snapshot).

### 3.7 Test vectors

Every vector below — every per-file hash and every aggregate `contentHash` — is computed directly
from the algorithm in §3.5, verifiable by the reproducible check in §9, not hand-written. Each vector
is a complete, standalone one-file `manifest.json`-style
inventory: `files[]` plus the resulting aggregate `contentHash`, so a reference implementation can
run each one directly and compare its own output against the value shown, not just against a bare
per-file digest.

**Vector A — a single empty file.**

```json
{
  "contentHash": "sha256:882ef778f1244d44d1d71833451255142ee99696fe4f0f389444e85fef24e281",
  "files": [
    { "path": "rules/empty.md", "length": 0, "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855" }

```

**Vector B — a single file with a non-ASCII path and non-ASCII content.** Path
`locales/café-日本語.json` (28 UTF-8 bytes), content the UTF-8 bytes of
`{"note":"Ünïcödé cöntent — café, 日本語, emoji 🎉"}` (64 bytes):

```json
{
  "contentHash": "sha256:bba288478a7635df6c3e5e04070ab7394411af80045048e6b0d87810f85591d6",
  "files": [
    { "path": "locales/café-日本語.json", "length": 64, "sha256": "d056096d06bd4e7d36319e8e808e12d7b0467c39ac85394017c1774b0e7ad3d4" }
  ]
}
```

**Vectors C1/C2 — the naive-concatenation-ambiguity pair, each as its own one-file set, and why the
framing in §3.5 resolves it.** These must be two separate, single-file inventories, not one combined
two-file inventory — a two-file set would let the file-level sort order do the disambiguating work
instead of the per-record length-prefix framing, which is the exact property this vector exists to
prove. Set C1 is the file `path="ab", content="cd"` alone; set C2 is the file `path="a",
content="bcd"` alone. Naive concatenation of `path + content` with no framing at all produces the
identical byte string `abcd` for both — a naive scheme literally cannot tell these two one-file sets
apart. The regression this vector proves is that, under the length-prefixed framing in §3.5, C1 and
C2 nonetheless produce **different** aggregate hashes, because the explicit length prefixes make the
path/content boundary unambiguous no matter what bytes either field contains:

```json
{
  "setC1": {
    "contentHash": "sha256:177859256ae03222541e92fd7fee332753511679dc06c20db3854fc6f783cef6",
    "files": [
      { "path": "ab", "length": 2, "sha256": "21e721c35a5823fdb452fa2f9f0a612c74fb952e06927489c6b27a43b817bed4" }
    ]
  },
  "setC2": {
    "contentHash": "sha256:af9f75dc8e547289c24c3ef2d5d0752561ffc3116cf9cd1577e2ca2c7dcc2134",
    "files": [
      { "path": "a", "length": 3, "sha256": "a6b0f90d2ac2b8d1f250c687301aef132049e9016df936680e81fa7bc7d81d70" }
    ]
  }
}
```

A reference implementation must reject any framing scheme that produces `setC1.contentHash ===
setC2.contentHash` for these two inputs — that equality is precisely the bug this vector exists to
catch, and every runtime's independent reimplementation of §3.5 must reproduce both hashes shown
above, distinct from each other, before it is trusted.

### 3.8 Runtime constraints on the vendored copy

- Runtime packages embed generated locale data (as JS already does via `src/generated/locales.ts`)
  and perform no network or filesystem access during ordinary `transform()` calls — a binding
  constraint (`docs/ARCHITECTURE.md` §4), unchanged by this split.
- `vendor/polytypo-spec/fixtures/` and `vendor/polytypo-spec/rules/` remain available in each
  runtime repository's own CI (needed for the conformance runner and for spec review), but are
  excluded from the published registry artifact — for JS specifically this is already true today:
  `package.json`'s `"files": ["dist"]` means `vendor/`, `tests/`, `scripts/` are never in the npm
  tarball regardless of this split. Each future runtime's packaging applies the equivalent exclusion
  in its own ecosystem's manifest (PyPI's `pyproject.toml` include-list, Go's already-implicit
  "only imported packages ship", RubyGems' gemspec `files`, Composer's `.gitattributes`
  `export-ignore`).

## 4. Spec update automation

### 4.1 Flow

1. A canonical spec/fixture change lands on `polytypo`'s trunk via ordinary PR review — spec-first,
   per `AGENTS.md`'s existing discipline, unchanged by this split.
2. `npm run validate:spec` (or its future canonical-only equivalent) passes on trunk.
3. An operator — a human, not automation — creates and pushes tag `spec-vX.Y.Z` on `polytypo`. Tag
   creation is not automated by any workflow this document adds; the audit plan's own execution
   order already treats tagging as its own deliberate, reviewed step, separate from any automatic CI
   action.
4. A `polytypo` workflow (`spec-tag.yml`, tag-push-triggered) first runs the integrity gates in
   §4.4 against the pushed tag, then — only if they all pass — computes the manifest (§3.3) and
   content hash (§3.5) for that tag, and **dispatches** a spec-update event to every runtime
   repository currently opted in to receiving it (§4.2–4.3 cover exactly how, and why the default
   `GITHUB_TOKEN` cannot do this alone).
5. Each runtime repository's `spec-update.yml` workflow (triggered by the dispatch) checks out the
   exact tagged canonical commit — never `main`/`master`, always the pinned tag — and independently
   recomputes the manifest and content hash using its own reference-tested implementation of §3.5,
   comparing every field against what the dispatch payload carried, per §3.6's full failure-mode
   list.
6. On successful verification: replaces `vendor/polytypo-spec/` wholesale (not a file-by-file diff
   — simpler, and matches "vendored, pinned, never fetched at runtime" semantics) and regenerates
   that runtime's embedded locale data.
7. Runs that runtime's complete gate: schema conformance of the newly vendored data, unit tests, the
   conformance runner against the new fixtures, idempotency property tests, lint, typecheck,
   packaging checks, build.
8. On verification failure (§3.6): **no PR is opened.** The workflow fails loudly, keeps its logs
   and any partial-computation artifacts for inspection, and stops — a snapshot that failed
   provenance/hash/schema verification must never reach a PR, draft or otherwise, because a human
   reviewing that PR could mistake "a PR exists" for "a verified snapshot exists."
9. On successful verification but a failing gate (step 7): a PR **is** opened, deliberately carrying
   a red/failing status, so a maintainer can see exactly what's incompatible. The distinction between
   step 8 and step 9 is the core failure-class split this document requires: unverified snapshot
   data never becomes a PR; a verified snapshot that the runtime can't yet build against does.
10. The PR sits for human review like any other PR — merging it only updates the source; it never
    runs `npm publish`/`pip upload`/etc. as a side effect. Publishing stays a separate, human-triggered
    action per runtime's own release workflow.
11. Once merged, the runtime's normal, unrelated release process may publish a new package version
    whenever its own maintainer chooses.

### 4.2 Event type and payload schema

Cross-repository dispatch uses GitHub's `repository_dispatch` API (`POST
/repos/{owner}/{repo}/dispatches`), not `workflow_dispatch`, which is same-repository only.
`POST /repos/{owner}/{repo}/dispatches` requires the **`Contents: write`** repository permission for
both fine-grained personal access tokens and GitHub App installation tokens — confirmed against
GitHub's own fine-grained-PAT permissions reference, which lists this exact endpoint under the
"Contents" permission at the `write` level with no additional permission required. The default
`GITHUB_TOKEN` cannot be used for this at all: its scope is limited to the repository whose workflow
generated it (GitHub's own `GITHUB_TOKEN` documentation states this directly), so any cross-repository
call — including this one — needs a GitHub App installation token or a personal access token instead.

Event type: `"spec-updated"`.

Payload (inert example, not wired to any live workflow in this repository):

```json
{
  "event_type": "spec-updated",
  "client_payload": {
    "dispatchSchemaVersion": "1.0.0",
    "specVersion": "0.4.0",
    "canonicalTag": "spec-v0.4.0",
    "canonicalCommit": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2",
    "contentHash": "sha256:6be8a405b3dae495af7ad8ab3d710840b499c50abefd8421ad0b42a2e3ef9627",
    "idempotencyKey": "spec-v0.4.0@a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2",
    "dispatchedAt": "2026-08-27T00:00:00Z"
  }
}
```

- **Idempotency key** — `"<canonicalTag>@<canonicalCommit>"`. A receiving runtime's
  `spec-update.yml` checks whether a branch matching this key already exists (e.g.
  `spec-sync/spec-v0.4.0-a1b2c3d`) before creating a new one — satisfying duplicate-dispatch
  handling without any external state store, since the runtime's own git remote is the source of
  truth for "does this branch/PR already exist."
- **Duplicate dispatch, same key:** if the branch exists and its PR is still open, the workflow
  updates the existing branch (a fresh commit, not a new branch/PR) rather than opening a duplicate.
  If the branch exists but its PR was closed by a human without merging (a maintainer explicitly
  rejected that spec update), the workflow does **not** silently reopen or recreate it — it posts a
  comment on the closed PR noting a new dispatch arrived for the same key, and stops; a human decided
  once, and a repeat dispatch for the exact same tag/commit does not get to override that decision
  automatically.
- **Superseded spec update:** if `spec-v0.4.1` tags before a runtime has merged its `spec-v0.4.0`
  update PR, the new dispatch's idempotency key differs, so it opens a second PR/branch rather than
  amending the first, and the ingestion workflow posts a comment on the older, still-open PR linking
  the newer one. The runtime maintainer decides whether to close the stale PR in favor of the newer
  one or merge both in sequence — a judgment call, not automated, since which spec version to adopt
  first can matter to a runtime mid-release.
- **Retry behavior.** `repository_dispatch` delivery is not itself retried by GitHub if the target
  repository is unreachable or the token lacks permission — the dispatching workflow checks the HTTP
  response of its own dispatch call and fails its own job loudly rather than swallowing a 404/403,
  so a broken dispatch is visible in `polytypo`'s own Actions log. No automatic retry-with-backoff is
  added for the dispatch call itself — a failed dispatch is a maintainer-visible signal to re-run the
  workflow manually.
- **Partial failure.** If dispatch succeeds for three of five runtimes and fails for two, the
  workflow reports per-target success/failure in its own job summary and fails the overall job if
  any target failed, so a human knows to re-run targeting just the failed ones.
- **A runtime that cannot conform** still gets its PR opened (step 4.1.9) with a failing gate — it
  does not block dispatch to, or publication by, any other runtime. §5's conformance matrix is the
  mechanism that keeps this honest without blocking anyone else.
- **Who may approve and merge.** The update PR is an ordinary PR against that runtime's default
  branch, subject to that repository's normal branch-protection/review rules. The automation itself
  is never granted merge rights.

### 4.3 Permissions and authentication boundary

- **`polytypo`'s `spec-tag.yml`** (the dispatcher) needs a credential that can call
  `POST /repos/{owner}/{repo}/dispatches` on each target runtime repository — the exact `Contents:
  write` permission cited in §4.2.
  - **Preferred: a narrowly scoped GitHub App.** A GitHub App owned by the `polytypo` GitHub
    organization, installed only on the runtime repositories it dispatches to, granted exactly
    `Contents: write` on those repositories — the exact permission the dispatch endpoint requires;
    neither `Administration` nor a lesser read-only grant. §5.1 below adds `Actions: read` to this
    same App for report ingestion, since both needs live on the same one credential rather than two. The
    app's installation access token is short-lived (on the order of an hour) and scoped only to the
    repositories the app is installed on — materially narrower blast radius than a PAT if
    `polytypo`'s Actions environment is ever compromised.
  - **Fallback: a fine-grained personal access token (PAT).** Scoped to exactly the runtime
    repositories, with `Contents: write`. Documented risks: a PAT is tied to the individual GitHub
    account that created it and stops working if that account loses org access or the token is
    revoked/expires; unlike a GitHub App token it is not automatically scoped to only the
    repositories a specific automation was installed on; a leaked fine-grained PAT is valid until
    its own expiry or manual revocation, not minutes; and using a named person's PAT for
    organization automation is an audit-trail smell — actions appear attributed to that person, not
    to "the spec-sync bot." Use only as a bridge until a GitHub App is set up.
- **Each runtime's own `spec-update.yml`** (the receiver) needs the ordinary same-repository
  `GITHUB_TOKEN`, with two repository-level grants:
  - `contents: write` and `pull-requests: write`, set in the workflow's own `permissions:` block;
  - the repository (or organization) setting **"Allow GitHub Actions to create and approve pull
    requests"** enabled under Settings → Actions → General → Workflow permissions — without it,
    `GITHUB_TOKEN` cannot open a PR at all, regardless of the workflow-level `permissions:` block.
  - No cross-repository credential is needed on the receiving side for opening the PR — it reads
    the public canonical repository's tagged content over a plain, unauthenticated `git
    fetch`/HTTPS archive download, then only writes to its own repository.
- **What `GITHUB_TOKEN`-opened PRs actually do, precisely, per GitHub's own documentation:**
  - Ordinary pushes made using `GITHUB_TOKEN` do not recursively trigger `push`-triggered workflow
    runs — GitHub's documentation states plainly that events triggered by `GITHUB_TOKEN` do not
    create a new workflow run, with `workflow_dispatch` and `repository_dispatch` as the only
    exceptions, specifically to prevent accidental recursive workflow chains.
  - A pull request created or updated using `GITHUB_TOKEN` **does** trigger `pull_request` workflow
    runs, but they start in an **approval-required** state: the PR shows a banner in the merge box,
    and a user with write access must explicitly select "Approve workflows to run" before those
    checks execute.
  - If fully automatic (non-approval-required) PR CI is wanted instead, the PR must be opened with a
    GitHub App installation token or a PAT, not `GITHUB_TOKEN` — GitHub's own documentation states
    this as the direct alternative.
- **Chosen policy (the lower-secret design, per the explicit preference):** the runtime's own
  `GITHUB_TOKEN` opens the spec-update PR — no cross-repository-capable credential is needed inside
  the receiving runtime repository at all. §4.1 steps 6–9 (verify, update, run the full gate) all
  happen **inside the same workflow run, before the branch is pushed and the PR opened** — so the
  PR, when it appears, already carries a completed, known gate result in its description/checks
  summary, not an unknown pending one. The `pull_request`-triggered CI run that then starts in
  approval-required state is not the thing maintainers are relying on to first learn whether the
  update is safe — it is a maintainer-visible re-confirmation step, approved as part of ordinary PR
  review, consistent with normal branch-protection practice. This avoids ever placing a
  cross-repository-write-capable token inside any of the (eventually five) runtime repositories,
  which only the canonical repository's dispatcher and report-ingestion workflows need.

### 4.4 Spec-tag integrity gates

Everything in §4.1–4.3 assumes the tag `spec-tag.yml` reacts to is trustworthy. That assumption is
checked, not assumed, by gates that run **before** `spec-tag.yml` computes a manifest or dispatches
anything:

- **The tag name must exactly match the trimmed contents of `spec/VERSION` at the tagged commit.**
  `spec-v0.4.0` is only valid if `spec/VERSION` at that exact commit reads `0.4.0` (whitespace-
  trimmed) — a tag pushed against the wrong commit, or a `spec/VERSION` that was edited without a
  matching tag, both fail this check rather than silently dispatching a mismatched pair.
- **The tag must resolve to the recorded full commit SHA**, and that SHA — not just the tag name —
  is what `spec-tag.yml` reads `spec/` from and what it places in the manifest's `canonicalCommit`
  field (§3.3) and the dispatch payload's `canonicalCommit` field (§4.2). The tag name is a
  human-facing label; the commit SHA is the thing every downstream check is actually anchored to.
- **Tag protection.** `spec-v*` must be covered by a tag protection rule or ruleset on the canonical
  repository that prevents an existing `spec-v*` tag from being silently force-moved to point at a
  different commit after the fact — without this, a tag's own immutability (which §3.3 already
  treats as not fully trustworthy, hence recording `canonicalCommit` separately) would have no
  actual enforcement behind it.
- **Snapshot source URLs prefer the immutable commit SHA over the movable tag name.**
  `manifest.json`'s `canonicalSourceUrl` (§3.3) should link to the exact commit
  (`.../tree/<canonicalCommit>/spec`) rather than only the tag
  (`.../tree/spec-v0.4.0/spec`) wherever both are shown, since the tag remains human-readable
  shorthand but the commit is what was actually verified.
- **Runtimes verify the commit, not just trust the payload's claim about it.** A receiving
  `spec-update.yml` fetches the commit SHA from the authenticated dispatch payload (§4.2), then
  independently confirms that `spec-vX.Y.Z` on the canonical repository currently resolves to that
  same SHA (a plain, unauthenticated read against the public canonical repository) before treating
  the payload as trustworthy — so a compromised or buggy dispatcher cannot simply assert an
  arbitrary commit SHA and have every runtime accept it without a second, independent point of
  confirmation.

## 5. Machine-readable conformance reports and matrix

### 5.1 Transport, chosen concretely

The public canonical matrix and the internal CI signal answer two different questions, and this
design keeps them structurally separate rather than conflating "the default branch currently
builds" with "the latest published release conforms":

- **Default-branch (CI) evidence** — mandatory on every relevant change, proves the runtime's
  in-development state currently conforms. Informative and developer-facing. Never, by itself,
  populates the public matrix's headline row.
- **Release evidence** — describes the runtime's latest *published* release: an exact tag, an exact
  registry-published package version, and an exact commit, cross-verified against each other and
  against the registry using that ecosystem's own provenance mechanism (§5.4). This is what the
  public canonical matrix's headline row shows.

The transport:

1. Each runtime repository has a dedicated `conformance-report.yml` workflow that always emits a
   versioned JSON report as a GitHub Actions build artifact, tagged `reportSubject: "default-branch"`
   (§5.2) — including on a run where the conformance/build gate itself failed, as long as report
   *generation* succeeded (a failing gate is itself a fact the report must state, via
   `overallStatus: "fail"`; only a crash during report generation itself should produce no artifact
   at all).
2. **Report cadence for default-branch evidence — required, not best-effort.**
   `conformance-report.yml` runs on every relevant change to the runtime's default branch (at
   minimum: anything touching `src/`, the vendored spec, or the conformance runner itself). A
   runtime implementation patch can introduce a conformance regression without changing
   `claimedSpec` at all (spec version unchanged, behavior changed), so "the spec version didn't
   change" is never a reason to skip generating a fresh report.
3. **Release evidence is generated by the runtime's own release workflow, not by
   `conformance-report.yml`.** That runtime's release gate (for JS, `.github/workflows/release.yml`,
   §6.3) already runs the complete conformance suite before publishing; it additionally emits the
   same versioned JSON report format, tagged `reportSubject: "release"` and carrying the `release`
   block described in §5.2, as a build artifact of that exact release run — the run that builds and
   publishes the exact commit being released, not a separate, later, or unrelated run. Canonical
   must never substitute a default-branch report for missing or failing release evidence, and must
   never present an older release's — or the current default branch's — green report as evidence
   for a release it does not itself describe.
4. `polytypo`'s GitHub App (§4.3) is additionally installed with the **`Actions: read`** repository
   permission on each runtime repository — the permission GitHub's own fine-grained-permissions
   reference lists as sufficient, with no additional permission required, for `GET
   /repos/{owner}/{repo}/actions/runs` (list workflow runs) and `GET
   /repos/{owner}/{repo}/actions/artifacts` (list/download artifacts). This is a second, separate
   permission grant from the `Contents: write` used for dispatch (§4.3) — the two are requested
   together on the same App installation, not as two different credentials.
5. A canonical `conformance-ingest.yml` workflow, triggered on a schedule and by manual
   `workflow_dispatch`, runs two independent queries per runtime, via the Actions API and each
   runtime's tag/release listing:
   - the latest **completed** run of `conformance-report.yml` on that runtime's default branch, for
     default-branch evidence;
   - the runtime's **stable-release selection**, and the exact release-workflow run that built and
     published it, for release evidence. Which release counts as "the" stable release is defined
     per ecosystem, never by a single universal rule — a highest-numbered SemVer tag is not
     sufficient by itself, since it could be an unreleased prerelease/pre-major tag that was never
     meant to represent the public stable line. §5.4 defines npm's selector (the registry's `latest`
     dist-tag) precisely; a future runtime on a different registry defines its own equivalent
     selector using that registry's own concept of "the version consumers get by default."
6. For each, it downloads the report artifact and verifies, before trusting anything in it:
   - the source repository matches the expected runtime repository name;
   - the workflow identity matches the expected workflow file for that evidence kind (not some other
     workflow that happens to have uploaded a similarly named artifact);
   - the run ID is the one just queried (not stale/cached data);
   - **for default-branch evidence only**, the runtime repository's current default-branch HEAD
     commit is fetched independently and compared: `workflow head_sha === report.runtimeCommit
     === current default-branch HEAD`. A relevant change can reach the default branch without
     `conformance-report.yml` ever running against it — a path-filter misconfiguration, a workflow
     disabled by mistake, a run that failed to trigger — and the latest *completed run that did
     happen* would otherwise be silently treated as describing the branch's current state when it
     does not. If the three values do not all match, default-branch evidence is not current: record
     `evidence: "unverified"` with reason `default-branch-head-mismatch`, never `pass`. This check
     has no equivalent for release evidence, which is anchored to an immutable tag and commit rather
     than a moving branch tip, and never applies to, or changes, the public matrix's release-only
     headline row (§5.3);
   - `head_sha` of that run equals the report's own self-declared `runtimeCommit` field — this
     specifically catches a report whose file content doesn't actually correspond to the commit the
     run claims to have built;
   - the artifact name matches the documented convention;
   - the report's JSON validates against its schema (§5.2), including `reportSubject` matching the
     kind of evidence being ingested;
   - the report's `claimedSpec` block (`specVersion`/`canonicalTag`/`canonicalCommit`/`contentHash`)
     is checked against canonical's own tag/commit/hash data for that `specVersion`;
   - **for release evidence only**, the full ecosystem-specific provenance chain in §5.4.
7. **An artifact that fails any check in step 6 is never stored as, or treated as, a verified
   report.** It is not written to `conformance/reports/<runtime>.json` under any circumstances —
   that path holds only artifacts that passed every check. Its raw content may be retained only as
   an ordinary, quarantined CI log/artifact reference (the failed `conformance-ingest.yml` run's own
   logs, which already exist as a normal GitHub Actions record) — never copied into the trusted
   report path, and never treated as if it were a verified report that merely has a bad status. What
   *does* get recorded, unconditionally, is the failure itself: an update to the durable evidence
   envelope described in §5.3, with the specific reason (`hash-mismatch`, `unverified`, schema
   validation failure, missing artifact, provenance-chain failure, …).
8. On success, canonical stores the report, normalized, at `conformance/reports/<runtime>-{release
   |default-branch}.json` (§1.8) **and** updates that runtime's durable evidence envelope (§5.3) —
   the `release` and `defaultBranch` sub-objects independently — to reflect the new verified state.
   On failure, only the relevant sub-object of the evidence envelope is updated — a stored report
   file, if one exists from a prior successful ingestion of that same evidence kind, is left as the
   historical last-known-good report, but it is the envelope, not the presence of that file, that
   the matrix reads to decide current status.
9. Every change to `conformance/reports/`, `conformance/state/`, and the generated
   `docs/CONFORMANCE_MATRIX.md` arrives through an ordinary canonical PR opened by
   `conformance-ingest.yml` — never a direct push to trunk, on both the success and the failure
   path — so a human reviews what the matrix is about to claim before it becomes canonical's own
   public statement about runtime conformance. `conformance-ingest.yml`'s own PR creation needs
   exactly the same `GITHUB_TOKEN` grants documented for the spec-update receiver in §4.3
   (`contents: write` and `pull-requests: write` in the workflow's `permissions:` block, plus the
   repository/organization "Allow GitHub Actions to create and approve pull requests" setting), or,
   for fully automatic non-approval-required ingestion CI, the same GitHub App or PAT already
   provisioned for dispatch/ingestion in §4.3, per GitHub's own documented alternative to
   `GITHUB_TOKEN` for that purpose. §4.3's chosen policy (`GITHUB_TOKEN`, approval-required) applies
   here unless an operator decides otherwise for this workflow specifically.
10. **Retention.** GitHub's own documentation states the default artifact retention period is 90
    days, and a public repository cannot configure it longer than 90 days. If `conformance-ingest.yml`
    cannot find a completed run within a bounded lookback window (a config value, no longer than the
    retention ceiling), or the most recent run it finds has no downloadable artifact left (expired,
    deleted, or never uploaded), that is itself a step-7 failure for the affected evidence kind — the
    corresponding sub-object of the evidence envelope is updated with `evidence: "absent"` and the
    specific reason ("no completed run found," "artifact expired," …), through the same canonical PR
    path as any other ingestion failure.

```json
  "runtimeCommit": "b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3",
  "claimedSpec": {
    "specVersion": "0.4.0",
    "canonicalTag": "spec-v0.4.0",
    "canonicalCommit": "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4e5f6a1b2",
    "contentHash": "sha256:6be8a405b3dae495af7ad8ab3d710840b499c50abefd8421ad0b42a2e3ef9627"

  "release": {
    "releaseTag": "v1.4.0",
    "registryEcosystem": "npm",

  "ciRunUrl": "https://github.com/polytypo/polytypo-js/actions/runs/0000000000"

```

`reportSubject` is exactly one of `"default-branch"` or `"release"`. The `release` object is present
if and only if `reportSubject === "release"`; a default-branch report omits it entirely — there is no
release to describe yet, and no field should exist that could be misread as claiming one.

`overallStatus` is restricted to exactly two values, **`"pass"` or `"fail"`** — a runtime reports
only on itself; it has no basis to claim `stale`/`absent`/`unverified`/`hash-mismatch`/`ahead`,
which are all judgments canonical makes by comparing the report (and, for release evidence, the
registry) against canonical's own data (§5.3, §5.4). A schema that let a runtime self-report `stale`
would let a misbehaving or out-of-date runtime simply not report accurately about itself; keeping
the runtime-facing enum to two values removes that option entirely — every richer status is
computed, never claimed.

`implementationVersion` and `claimedSpec.specVersion` are two different fields on purpose — runtime
package versions stay independent of spec versions. `release.registryPackage` (the published
registry name, `polytypo`) and `runtimeRepository` (the source repository name,
`github.com/polytypo/polytypo-js`) are two different fields for the same reason — a package name, a
repository name, and a spec tag (`spec-vX.Y.Z`) are three distinct identifiers, never used
interchangeably anywhere in this schema.

### 5.3 Durable evidence envelope and canonical-derived matrix status

A design that renders `absent` for an expired or missing artifact, but otherwise leaves a
previously stored report file untouched on a failed ingestion, creates a real hazard: a later, naive
matrix regeneration could re-read that untouched, now-stale file and display it as passing again,
silently reintroducing exactly the staleness §5.1 step 10 exists to prevent. The durable evidence
envelope closes that hazard structurally: it is the one thing ingestion *always* writes to, on both
the success and the failure path (§5.1 steps 7–8), for both evidence kinds independently, so the
matrix never has to infer current status from a report file's mere presence.

**Envelope location:** `conformance/state/<runtime>.json` (§1.8), one envelope per runtime, holding
`release` and `defaultBranch` as independent sub-objects. **Raw, once-verified reports may still
live under `conformance/reports/`** as last-known-good historical artifacts, but the matrix
generator reads the envelope, never a raw report file directly, for status — and the **public
canonical matrix's headline row for a runtime is the envelope's `release` sub-object only**; the
`defaultBranch` sub-object is shown, if at all, as a separate, clearly labeled CI-status column, never
merged into the release row.


- `matrixTargetSpecTag` is the latest stable canonical `spec-v*` tag recorded at the moment this
  envelope was last regenerated — the explicit comparison point the `currency` dimension (below) is
  computed against, rather than an implicit "whatever the latest tag happens to be right now," which
  would make `currency` a moving target mid-regeneration.
- `lastIngestionAttempt` records the *most recent* attempt for that evidence kind, success or
  failure — this is what lets a human see "release-evidence ingestion has been failing for the last
  five scheduled runs" even while `lastVerifiedReport` still points at an old, once-good report.
- `lastVerifiedReport` records the most recent attempt that actually passed every §5.1 step 6 check
  (and, for `release`, §5.4's provenance chain) — absent, or unchanged from a prior envelope version,
  when the most recent attempt failed.
- `release.subject` and `provenanceVerified` exist only in the `release` sub-object — there is no
  registry publication to describe for default-branch evidence, and `provenanceVerified` is the
  explicit, machine-readable record that §5.4's ecosystem-specific chain was actually run and passed,
  not merely that a version number happened to match.
- `reason` is populated (a short machine-stable code plus a human-readable string) whenever that
  sub-object's `currentEvidence.evidence` is anything other than `"verified"` — the specific check
  that failed (`hash-mismatch`, `unverified`, `schema-invalid`, `artifact-missing`,
  `artifact-expired`, `head-sha-mismatch`, `default-branch-head-mismatch`, `provenance-chain-failed`,
  `no-release-exists`, …).
- **Timestamps here are expected and required** — `attemptedAt`/`verifiedAt` are external evidence
  about when canonical *observed* a fact, not part of any deterministic spec snapshot. This is
  deliberately different from §3.3's manifest, which excludes timestamps because the manifest must
  hash identically across repeated runs over the same input; the evidence envelope has no such
  determinism requirement — it is a record of canonical's own observation history, and recording
  that history's timing is the point of the record.

**Four independent dimensions per evidence kind**, not one enum conflating them. A single flat
status value cannot represent, for example, a failed release report against an old spec version
(both `fail` and `stale` at once) or a partial but current pass (both `pass` and `partial` at once).
Each dimension is independently computed and independently displayed:

| Dimension | Values | Meaning |
|---|---|---|
| `evidence` | `verified` \| `absent` \| `unverified` \| `hash-mismatch` | Whether canonical currently holds a trustworthy, provenance-checked report for this evidence kind at all — computed from §5.1 step 6's checks (plus §5.4 for `release`), independent of what that report says. **This is the gate for every other dimension**: nothing below is ever computed from a report that didn't pass this one. |
| `conformance` | `pass` \| `fail` \| `unknown` | The verified report's own `overallStatus`. Forced to `unknown` whenever `evidence !== "verified"` — there is nothing trustworthy to read a pass/fail from. |
| `currency` | `current` \| `stale` \| `ahead` \| `unknown` | How the verified report's `claimedSpec.canonicalTag` compares to `matrixTargetSpecTag` (below). Forced to `unknown` whenever `evidence !== "verified"`. |
| `coverage` | `full` \| `partial` \| `unknown` | Whether `localeCoverage`/`supportedModes` cover the full canonical set. Forced to `unknown` whenever `evidence !== "verified"`. |

**`currency`, precisely, and why `ahead` cannot occur for anything unverified.** Compute `currency`
only when `evidence === "verified"`; every other case is `unknown` by the hard rule above — an
untagged, nonexistent, hash-mismatched, or otherwise unverifiable spec claim is `evidence:
"unverified"` or `"hash-mismatch"`, never `currency: "ahead"`, because `ahead` is a judgment about a
*confirmed-real* tag's position relative to the target, and a claim that failed verification has no
confirmed-real tag to judge the position of. Given a verified report:

1. Strip the literal `spec-v` prefix from both the report's `claimedSpec.canonicalTag` and from
   `matrixTargetSpecTag`. If either does not start with exactly that prefix, `currency: "unknown"`.
2. Validate each remainder as SemVer (`MAJOR.MINOR.PATCH`, with optional pre-release/build metadata
   per semver.org). If either fails to parse as valid SemVer, `currency: "unknown"` — ordering is
   never guessed from an unparseable string.
3. Compare using standard SemVer precedence. Equal → `current`. Report's version is lower →
   `stale`. Report's version is higher → `ahead`.

`ahead` is possible only because the report is already fully verified — the reported tag and commit
independently checked out and hash-matched against canonical's own data — and is a real, cut
canonical spec tag that simply postdates the matrix's own currently configured target. This is the
expected shape of an intentional staged rollout (canonical cuts `spec-v0.5.0` before every runtime,
and the matrix's own target, is deliberately bumped to match) or a narrow update race, never a
placeholder for "something about this claim couldn't be trusted" — that case is always `unverified`
or `hash-mismatch` in the `evidence` dimension instead.

A failed release report against an old spec is representable exactly as required:
`evidence: verified`, `conformance: fail`, `currency: stale`. A partial but current pass is
`evidence: verified`, `conformance: pass`, `currency: current`, `coverage: partial`. Neither is
expressible as one flat status value.

**Single-value display rollup**, for a matrix column that wants one glance-able value, applies this
explicit precedence — first match wins, and `ahead` is checked explicitly rather than falling
through to `pass`:

1. `evidence !== "verified"` → show the `evidence` value itself (`absent` / `unverified` /
   `hash-mismatch`);
2. `conformance === "fail"` → `fail`;
3. `currency === "stale"` → `stale`;
4. `currency === "ahead"` → `ahead`;
5. `coverage === "partial"` → `partial`;
6. otherwise → `pass`.

This rollup is a display convenience only, computed from the `release` sub-object for the public
matrix's headline row — the four machine-readable dimensions above are what any tooling, and any
future runtime's own status check, actually reads.

### 5.4 Release provenance verification, per ecosystem

Release evidence is trustworthy only if canonical can independently confirm that the exact package
version a registry publishes is the exact commit the release report describes — not merely that a
version number and a commit both happen to be present in the same report. This chain has five links,
checked in order, and **failing any of them means release evidence is `absent` or `unverified`,
never `pass`** — there is no partial credit:

1. The runtime's release tag (`release.releaseTag`, e.g. `v1.4.0`) resolves, in the runtime
   repository, to exactly `runtimeCommit`.
2. The declared package version (`release.registryVersion`) matches both the tag (`v1.4.0` ↔
   `1.4.0`) and the package manifest's own version field read at that exact commit (`package.json`'s
   `"version"` for npm).
3. The registry's actually-published artifact for that version corresponds to that same commit,
   confirmed through whatever provenance mechanism that specific ecosystem's registry provides.
4. The ingested workflow run is the same run that built and published that commit — not a separate,
   later report claiming to describe an already-published release.
5. No older default-branch report, and no older release's report, is ever substituted for a missing
   or failed check on the release currently being evaluated.

**This document does not invent a universal registry-to-commit mapping** — no such single mechanism
exists across npm, PyPI, Go modules, RubyGems, and Packagist. Step 3 is defined per ecosystem,
fail-closed: an ecosystem with no available provenance mechanism yields `evidence: "unverified"` for
every release from that ecosystem until one is defined, never a `pass` obtained by skipping the
check.

**npm (the only currently relevant ecosystem).** `.github/workflows/release.yml` already publishes
with `npm publish ... --provenance` (§1.2), which attaches a Sigstore-backed provenance attestation
binding the published tarball to the source repository, commit, and GitHub Actions workflow run that
produced it. npm's own documentation is specific about how that attestation is actually checked, and
this design follows it exactly rather than assuming a shortcut:

- [`npm audit signatures`](https://docs.npmjs.com/cli/audit/) verifies the registry signatures and
  provenance attestations of packages already present in the current project's dependency tree — it
  operates on installed dependencies (via `npm install`/`npm ci` and a lockfile), not on an arbitrary
  `package@version` spec passed directly. There is no documented npm CLI or registry mechanism that
  returns a verified attestation for a bare package identifier without installing it first.
- [Generating provenance statements](https://docs.npmjs.com/generating-provenance-statements/) and
  [Viewing package provenance](https://docs.npmjs.com/viewing-package-provenance/) describe what an
  attestation records (a link to the source repository and build environment, Sigstore
  transparency-log entries) and how a human views one (the registry web UI's provenance panel), but
  neither documents a stable, directly-queryable public API for fetching an attestation by
  `package@version` alone. Step 3 for npm therefore does not rely on any such endpoint.

Step 3 for npm, precisely, as a fail-closed sequence — every step must succeed in order, and any
failure anywhere in the sequence yields `evidence: "unverified"`, never a `pass` obtained by skipping
ahead:

1. Resolve the release under evaluation via the registry's `latest` dist-tag (`npm view polytypo
   dist-tags.latest`), never simply the numerically highest published SemVer — a prerelease or a
   channel other than `latest` must never silently stand in for the public stable row.
2. Create a disposable, empty project directory (never the checkout being verified, and never reused
   across verification runs).
3. Install exactly that resolved version with a lockfile: `npm install polytypo@<resolved-version>`
   (producing `package-lock.json` for that exact install), so the package actually being audited is
   pinned and reproducible.
4. Run a sufficiently recent npm CLI (npm ≥ 9.5.0, per npm's own stated requirement for provenance
   auditing) inside that disposable project: `npm audit signatures --json --include-attestations`.
   The exact machine-readable output shape must be validated against the npm CLI version actually in
   use at implementation time — this design does not assume a specific JSON schema it has not
   verified against a real CLI run.
5. Parse the verified attestation entry for exactly the installed `polytypo@<resolved-version>` — not
   any other package the disposable project's own tooling might have pulled in.
6. Verify, from that attestation, that the attested source repository, source commit, and workflow
   identity/run match `runtimeCommit` and `github.com/polytypo/polytypo-js` exactly, and that the
   attested artifact's integrity matches the release report's own declared identity.
7. Any missing field, ambiguous match, invalid signature, absent attestation, integrity mismatch, or
   output shape `npm audit signatures --json` does not actually produce is `evidence: "unverified"` —
   never a partial pass.

No release published without `--provenance` can satisfy this chain, which is already guaranteed by
the existing release workflow requiring `--provenance` unconditionally.

**Future ecosystems (Python/PyPI, Go, Ruby, PHP):** each future runtime repository's own equivalent
of this document must define its own step-3 mechanism using whatever provenance facility that
ecosystem's registry actually offers at the time that runtime is built (for example, PyPI's Trusted
Publishing/attestation support, or a Go module's content-addressed verification through the public
module checksum database) — not a mechanism assumed here in advance, and not skipped if the
ecosystem currently offers none.

### 5.5 Programmatic spec-version exposure

Every runtime must expose the spec version it conforms to programmatically, not only in its README.
For JS this is a small, already-half-done addition, not a new mechanism: `scripts/gen-locales.mjs`
already generates a `SPEC_VERSION` constant inside `src/generated/locales.ts` from `spec/VERSION`.
The remaining post-split task is exposing that existing generated constant through the intended
public entry point (e.g. re-exporting it from `src/index.ts` as `SPEC_VERSION`) and adding a test
that asserts it matches `spec/VERSION` — not adding version generation to `gen-locales.mjs` for the
first time, which already exists. Flagged as a concrete, low-effort follow-up in §12; not
implemented as part of this design.

## 6. Issue and release ownership

### 6.1 Issue routing table

| Symptom | Owning repository | Example |
|---|---|---|
| Wrong quote/dash/apostrophe/nbsp behavior for a locale | `polytypo` | "French guillemets should have a thin space, not a full nbsp, in this context" |
| Wrong or missing normative citation | `polytypo` | "The `de-CH` en-dash rule cites Duden but the linked edition doesn't say that" |
| Schema or fixture defect (not tied to one runtime's output) | `polytypo` | "`spec/schema/locale.schema.json` doesn't reject an empty `quotes.primary.open`" |
| JS packaging: wrong `exports` map, CJS/ESM interop failure, bundler can't tree-shake `polytypo/text` | `polytypo-js` | "Webpack still pulls in `parse5` when only importing `polytypo/text`" |
| Node-specific runtime bug (not a typography-correctness bug) | `polytypo-js` | "`transform()` throws on Node 20 but not 22 for a specific input length" |
| JS-side parser adapter defect (`parse5`/`micromark` integration bug, not a spec question) | `polytypo-js` | "HTML mode drops an attribute value when input contains a null byte" |
| Python/Go/Ruby/PHP implementation or packaging defect | that runtime's own repo, once it exists | "PyPI wheel is missing the `py.typed` marker" → `polytypo-python` |
| Site/brand/promo/documentation defect | `polytypo` | "Playground page overflows at 320px" |
| Cross-runtime conformance disagreement (two runtimes disagree on the same fixture) | `polytypo` first (either the spec is ambiguous or one runtime has a bug); re-routed to the specific runtime once triage shows only one implementation is wrong and the spec itself is unambiguous | "Go and JS disagree on `en-US` ellipsis + trailing punctuation for the same fixture input" |
| Spec-sync/dispatch/snapshot-manifest automation failure | `polytypo` if the dispatch itself failed (§4.2); the specific runtime's repo if that runtime's `spec-update.yml` failed after a successful dispatch | "The `spec-v0.4.1` dispatch never reached `polytypo-go`" → `polytypo`; "`polytypo-js`'s spec-update PR opened but its gate is red" → `polytypo-js` |

### 6.2 When an issue must be mirrored or linked

Only for the "cross-runtime conformance disagreement" and "dispatch failure" rows above, where the
same underlying fact is relevant to more than one repository's maintainers — link (not duplicate
content into) the issue once triage identifies which repositories are actually affected. Every
other row has exactly one owning repository and needs no mirroring. `polytypo` always owns the final
normative decision on any typography-correctness question, regardless of which repository an issue
was filed in — a runtime repository may propose a spec change but cannot unilaterally decide one,
the same spec-first discipline `AGENTS.md` already states, now applied across repositories too.

### 6.3 Release gates

| Release type | Gate |
|---|---|
| Canonical spec tag (`spec-vX.Y.Z`) | `validate:spec` green, the project's existing spec-first review process (schema, fixtures, and citation checks plus maintainer review) passed, an operator creates and pushes the tag — never automated (§4.1 step 3) |
| Canonical site release (GitHub Pages deploy) | Generated-artifact drift check green (§1.1/§2), a human triggers the deploy via `workflow_dispatch` (§7) |
| JS npm release | Unchanged from today's `release.yml`: full gate green, tag `v*` matching `package.json` version, `0.0.0` explicitly rejected by `scripts/verify-release-tag.mjs` |
| Future runtime registry releases | Each runtime's own equivalent of `release.yml` — not designed here; those repositories don't exist yet |

A runtime failing the latest spec does not block other conforming runtimes from publishing
implementation-only fixes for an older declared spec — mechanically true by construction, since
each runtime's `release.yml`-equivalent is entirely independent of every other runtime's CI and of
`polytypo`'s own tagging. Its status stays honest in the canonical matrix (§5) regardless of what it
publishes.

## 7. Canonical site and `polytypo.is-a.dev`

**GitHub Pages is live** (`https://polytypo.github.io/polytypo/`, deployed and verified end-to-end
via `pages-deploy.yml` on 2026-09-05 — every generated page, `robots.txt`, `sitemap.xml`, and asset
returns 200, and document-relative links resolve correctly at this project-page depth). The custom
domain is not yet attached — that is gated on the is-a.dev PR below, which is not filed by this
document either: no `domains/polytypo.json` commit, no fork, no PR.

### 7.1 Verified requirements and current state (primary sources, checked 2026-09-05)

- **Domain choice: `polytypo.is-a.dev`, not `polytypo.js.org`.** Superseded by operator decision —
  the project spans five planned runtimes, not only JavaScript, and js.org's own eligibility test
  ("directly related to the JavaScript ecosystem/community") is a narrower fit than a
  runtime-neutral domain.
- **is-a.dev submission process:** a PR against `is-a-dev/register` adding `domains/polytypo.json`;
  approval and exact-name availability are decisions of the is-a.dev maintainers, not guaranteed.
  Their own eligibility bar (Terms of Service §3–4): software-development-related, non-commercial —
  a typography library's documentation/demo site clears both.
- **Domains register to an individual GitHub account, never an organisation** (is-a.dev Terms of
  Service §2, verbatim: "Subdomains must be registered to an individual GitHub account, and cannot
  be registered to a GitHub organisation account."). `owner.username` in the registration file must
  be the personal account opening the PR, not the `polytypo` GitHub organisation that owns this
  repository — their CI checks the field against the PR author's own login and rejects a mismatch.
  The same ToS (§2.2, §3) explicitly permits an individual to register a domain "as a representative
  of ... a non-commercial project," so an open-source project registering this way is exercising
  their stated policy, not working around it.
- **Registration file schema**, path `domains/polytypo.json`:
  ```json
  {
    "owner": { "username": "<the personal GitHub login opening the PR>", "email": "<contact email>" },
    "records": { "CNAME": "polytypo.github.io" }
  }
  ```
  `records.CNAME` is a single string, not a list, and must be this site's real GitHub Pages
  hostname — `polytypo.github.io`, the org that owns the Pages-serving repository, regardless of
  which personal account registers the domain. If `records.CNAME` is present, no sibling key may
  appear alongside it in `records` (their own test suite enforces this). `owner.email` must be a
  real, reachable address — a `@users.noreply.github.com` address is rejected.
- **is-a.dev's Terms of Service explicitly prohibit using an AI tool to create the pull request,
  naming Claude Code specifically** (§6: "We are strongly against the usage of AI (such as Claude
  Code, Codex...) for creating pull requests, and may close the pull request ... if used"). The
  registration file's content can be prepared in advance (above); the fork, commit, and PR
  itself — including their required PR template's checkboxes and a working-site description — must
  be done by a human, not automated by this project's tooling or by an agent acting on its behalf.
- **GitHub Pages custom domain, workflow-based publishing.** GitHub's own documentation states
  plainly: "If you are publishing from a custom GitHub Actions workflow, no `CNAME` file is created,
  and any existing `CNAME` file is ignored and is not required." Branch-based Pages publishing is the
  mode that creates and consumes a `CNAME` file; workflow-based publishing (§7.3's design) does
  neither — it creates no `CNAME` file at all, and would ignore one if it somehow existed. Settings →
  Pages is, regardless of publishing mode, the authoritative place the custom domain is configured,
  but configuring it there does not itself create a `CNAME` file for a workflow-based deploy. Source:
  [GitHub — Managing a custom domain for your GitHub Pages site](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site).
- **HTTPS enforcement** is available under the same Settings → Pages panel once the custom domain is
  verified; GitHub's documentation notes it can take up to 24 hours to become available. Not
  testable or settable from this document.
- **Protected `github-pages` environment:** GitHub protects the `github-pages` deployment
  environment by default when Pages uses a GitHub Actions source, typically restricted to the
  repository's default branch; required reviewers can additionally be configured on that
  environment (up to six people or teams; only one approval is needed to proceed), and required
  reviewers are available on public repositories on every plan tier.

### 7.2 Current state of the site's build coupling — corrected

**Today, the generated playground and every generated example string are built from this monorepo's
local `src/index.ts`/`src/index.js`, not from any published npm package** — `promo/vendor/
polytypo.browser.js` is produced by `esbuild src/index.ts --bundle` and `promo/examples.json` is
produced by `gen_examples.ts` importing `../../src/index.js` directly (§1.3a/b). No claim anywhere
in this document should be read as saying the current site already runs the published `polytypo`
package — it does not, because no version of `polytypo` has been published yet. Running the
published package is the target post-split state, made a hard precondition of the split itself in
§2.1, not a description of today.

### 7.3 Hosting design (deployed and verified 2026-09-05)

- **Host:** GitHub Pages, deployed from `polytypo` (canonical) via `actions/deploy-pages`, publishing
  the `promo/` directory as the site root — chosen over branch-based Pages publishing since branch
  publishing would need a second place generated output lives (a `gh-pages`-style branch), when
  `promo/` is already the deterministic generated output on the trunk branch.
- **Deployment trigger — exactly one, not two contradictory ones.** The deploy workflow
  (`pages-deploy.yml`, §1.8) is triggered **only** by manual `workflow_dispatch`, taking the exact
  commit SHA to deploy as an input. It is not triggered automatically on every trunk push, and PR
  workflows never deploy at all.
- **Commit provenance is checked before the site is even built, not assumed from the input alone.**
  A `workflow_dispatch` accepting an arbitrary SHA string must not deploy an unreviewed repository
  object merely because a human later approves the `github-pages` environment prompt — the
  environment approval is an *additional* gate on top of commit provenance, never a substitute for
  it. Before building or deploying anything, the workflow verifies, and fails closed if any check
  does not hold:
  - the requested commit exists in the canonical repository at all (a typo'd or garbage SHA fails
    here, immediately);
  - the commit is either an ancestor of canonical's protected default branch, **or** it exactly
    matches one of an explicitly allowed set of protected site-release tags (so a deliberately
    tagged release commit can be redeployed later without needing to still be reachable from the
    then-current tip of the default branch);
  - the commit has a passing, required canonical CI result recorded for that exact SHA (not merely
    "some CI run exists somewhere for this repository," and not a CI result for a different commit
    on the same branch).

  Only once all three hold does the run proceed to: check out that exact commit, regenerate the site
  (`npm run generate:all`-equivalent), require **zero** generated-artifact drift against what's
  already committed at that commit (the same drift check CI already runs, re-run here as a
  belt-and-suspenders gate), and upload exactly that commit's `promo/` directory as the Pages
  artifact. The job then runs against the protected `github-pages` environment (§7.1), which adds a
  named reviewer's approval **on top of** the provenance checks above — meaning every real
  production deploy requires an explicitly named, provenance-verified commit *and* a separate human
  approval, with no path in this design where either check alone is sufficient, and no path where a
  push to trunk alone causes a live-site change.
- **Custom domain / CNAME ownership:** configured via repository Settings → Pages on `polytypo` by a
  repository admin, once is-a.dev approves the PR (§7.1). No `CNAME` file is created or required for
  this workflow-based deploy — see §7.1's corrected citation of GitHub's own documentation on this
  point; this document does not claim the Settings UI action creates one.
- **HTTPS:** "Enforce HTTPS" enabled in the same panel once available; not settable from this
  document.
- **Relative links and direct-page URLs:** `promo/`'s generated pages are directory indexes served
  at directory URLs (`/docs`, `/playground`, `/locales`, `/manifesto`; home at `/`), and link to
  each other with document-relative, trailing-slash hrefs (`docs/` from the root page,
  `../docs/` from a nested one). Being document-relative rather than root-relative, they need no
  rewriting either for a root-path custom-domain deploy (`polytypo.is-a.dev/`) or for the
  project-page path the site is served from before is-a.dev approves the custom domain
  (`polytypo.github.io/polytypo/` — verified live at this exact path, §7).
- **Cache-safe asset naming — a required pre-launch gate, not one of two equally acceptable
  options.** Today's generated filenames (`promo/vendor/polytypo.browser.js`, `promo/assets/site.js`,
  `promo/assets/style.css`) are fixed, not content-addressed — a changed bundle keeps the same
  filename across deploys. GitHub Pages provides no per-file cache-header control, and a complete,
  verified redeploy (the design above) does **not** by itself invalidate a browser's or an
  intermediary cache's copy of a fixed URL — "the deploy was clean and complete" and "every visitor
  is actually seeing the new bytes" are different claims, and fixed filenames make the second one
  unverifiable from the deploy side alone. Before any public Pages launch, the generator must be
  extended to emit content-hashed filenames for every mutable JS/CSS asset — the browser engine
  bundle, the shared site JavaScript, and the shared stylesheet — with the generated HTML referencing
  the matching hashes deterministically, the same content-derived-hash discipline already required
  of `tsup`'s own chunk output (§2.12). Stable page URLs (`/`, `/playground`, …) are
  unaffected and remain unchanged. Because HTML and its referenced assets deploy atomically as one
  Pages artifact, an old hashed asset file that no HTML in the new artifact references anymore may
  simply be dropped from that artifact — there is no orphaned-reference risk, since nothing in the
  newly deployed HTML could still be pointing at it. **This is a concrete, scoped generator change
  flagged as a pre-launch implementation gate (§12) — not implemented in this documentation-only
  pass**, and no Pages deploy should be treated as launch-ready before it lands.
- **No redirect away from `polytypo.is-a.dev`:** satisfied by construction — nothing in the generated
  site's templates emits a redirect, and this design adds none.
- **No analytics/external services:** satisfied by construction, continuing the existing privacy
  posture — `tests/promo/` already asserts no tracker/analytics call exists in the generated output.
- **Preview builds that cannot overwrite production:** satisfied by construction of the trigger
  design above — there is no automatic-on-push path to production at all, manual or otherwise, for
  any branch other than the explicit commit an approver chose to deploy; a PR that changes `promo/`
  is reviewed via its regenerated-artifact diff in ordinary CI, which never touches the live Pages
  deployment.

package file. Its own internal consistency is nonetheless checkable by reproducible, mechanical
means. This section specifies each check precisely enough to rerun, states the algorithm or command
it uses, and gives the result that check must produce for this document to be considered internally
consistent.

**JSON well-formedness.** Every fenced ` ```json ` code block in this document must parse as valid
JSON. Check: extract each block and parse it with any standard JSON parser (`json.loads` in Python,
`JSON.parse` in JavaScript). Required result: every block parses without error.

**Hash test vectors are genuine, reproducible computations, not placeholders.** §3.3's worked
example and §3.7's Vectors A, B, C1, and C2 must each recompute, byte-for-byte, to the exact
`sha256` and `contentHash` values printed alongside them, using exactly the algorithm specified in

differs from Vector C2's aggregate despite both file sets' naive `path + content` concatenation
producing the identical byte string `abcd` — this is the specific property §3.5's framing exists to
guarantee, and the vectors exist to prove it holds.

**Section reference validity — one parser, one pass, qualified and local references validated
against different heading sets.** This document's cross-reference syntax is normalized to exactly
two forms, each unambiguous by construction:

- **Qualified**, meaning "this section number belongs to a different document": a backtick-quoted
  Markdown path ending in `.md`, then whitespace (which may include a line break — the two are never
  required to sit on the same line), then `§N` or `§N.M`, optionally followed by a range whose second
  bound is a bare number with **no repeated `§`** — `` `docs/FILE.md` §N.M–P.Q ``, never
  `` `docs/FILE.md` §N.M–§P.Q ``. Repeating `§` before a range's second bound is invalid syntax in
  this document: it lets a naive extractor treat the second bound as an independent, unqualified
  reference and validate it against the wrong document's headings, silently passing whenever the two
  documents happen to share a heading number by coincidence rather than by the reference actually
  being correct.
- **Local**, meaning "this section number belongs to this document": `§N` or `§N.M`, in every case
  not matching the qualified form above — with the same single-`§` range rule (`§N.M–P.Q`, not
  `§N.M–§P.Q`).

Check: a single regular expression, evaluated in one pass (not two separate passes that first
extract qualified references and then treat whatever text is left over as local — that two-pass
shape is exactly what let a range's second bound go unclassified or misclassified):

```text
(?:`([\w./-]+\.md)`\s+)?§(\d+(?:\.\d+)?)(?:[–—-](\d+(?:\.\d+)?))?
```

For each match: if the path group is present, both captured bounds (the base number and, if present,
the range's second bound) are validated against that path's own extracted numbered headings; if the
path group is absent, both captured bounds are validated against this document's own extracted
numbered headings. `docs/ROADMAP.md` never appears as a qualified target here because it has no
numbered headings — its milestones (M0–M5, Phase A–D) are referenced by name, never by `§`.

A reference must be this document's own live cross-reference to be evaluated at all; a section
number named only while stating a general rule about syntax (as in this paragraph's own worked
example above, which uses letters — `N`, `M`, `P`, `Q` — rather than digits, and therefore never
matches the numeric pattern the check itself uses) is not a reference the check counts.

Required result, run against this document as it stands: **7 qualified references (8 section
bounds, one of them a range) and 228 local references (231 section bounds, three of them ranges),
zero unresolved in either category.**

## 10. Security considerations

- **The cross-repository dispatch-and-ingestion credential (§4.3, §5.1)** is the single
  highest-blast-radius piece of this design: one GitHub App holding both `Contents: write` (dispatch)
  and `Actions: read` (report ingestion) across every runtime repository. It must be scoped to
  exactly those repositories, never org-wide, and the App-over-PAT preference exists specifically to
  bound both the scope and the lifetime of that credential.
- **The vendored snapshot's manifest and hash (§3) are the tamper-evidence mechanism, not a secrecy
  mechanism** — they let a runtime, and canonical's `evidence: hash-mismatch` state (§5.3), detect an
  accidentally or maliciously modified vendored copy, including a missing or added file (§3.4's
  authenticated inventory), but they do not themselves prevent a compromised dispatch credential
  from pushing a correctly-hashed but maliciously chosen spec commit. The actual defense against that
  is ordinary PR review on the canonical spec change itself (§4.1 step 1), before any tag or dispatch
  happens.
- **No secret needs to reach a receiving runtime's `spec-update.yml`** (§4.3) — it only reads public
  canonical content over unauthenticated HTTPS and writes to its own repository with its own
  ordinary `GITHUB_TOKEN`. This keeps the number of repositories holding the cross-repository
  dispatch/ingestion credential to exactly one (`polytypo`), not five.
- **`npm publish`'s existing provenance/OIDC design (`release.yml`, unchanged)** already follows the
  narrowest-permission pattern this document recommends elsewhere (`id-token: write` granted only to
  the one job that needs it) — cited as existing precedent this design's credential handling stays
  consistent with.

## 11. Failure and recovery plan (cross-reference summary)

| Failure | Where handled |
|---|---|
| First npm release doesn't exist yet | §2.1 — hard NO-GO, not a workaround |
| History-filter step produces an unexpected result | §2.5 backup/bundle, §2.11 rollback |
| A ref/tag/branch is missed or wrongly discarded | §2.6 explicit freeze-time enumeration requirement |
| A cross-cutting open PR blocks a clean filter | §2.10 |
| Post-split JS package differs from pre-split monorepo build | §2.12 equivalence checklist |
| Snapshot fails provenance/hash/schema verification | §3.6, §4.1 step 8 — no PR opened, fail loudly |
| Snapshot verifies but the runtime's gate fails | §4.1 step 9 — draft/red PR opened for inspection |
| Dispatch fails to reach a runtime repo | §4.2 retry/partial-failure handling |
| Duplicate dispatch, or dispatch after a human closed the prior PR | §4.2 |
| A runtime's vendored snapshot is hand-edited or corrupted | §5.3 `evidence: hash-mismatch`, §3.3 `generatedFileWarning` |
| A runtime falls behind the latest spec | §5.3 `currency: stale`, §6.3 (does not block other runtimes) |
| A conformance report artifact expires or was never produced | §5.1 step 10, §5.3 `evidence: absent` |
| A release's registry publication can't be tied to its claimed commit | §5.4 provenance chain — `evidence: unverified`, never `pass` |
| No release exists yet for a runtime | §5.4 — `evidence: absent` for the release row; default-branch evidence is unaffected and shown separately |
| A verified report claims a spec tag newer than the matrix's own target | §5.3 `currency: ahead` — expected during a staged rollout, shown explicitly, never rolled up into `pass` |
| Dispatch/ingestion credential compromised | §10 |
| Pages deploy accidentally triggered by a push | §7.3 — not possible by construction (manual `workflow_dispatch` only) |
| Pages deploy given an arbitrary/unreviewed commit SHA | §7.3 — commit-provenance checks (ancestry or allowed release tag, plus required CI) run before build, independent of environment approval |
| Deployed asset served stale from a cache after a redeploy | §7.3 — content-hashed asset filenames (pre-launch gate, not yet implemented) |

## 14. Cross-document alignment

Four documents describe overlapping parts of the repository-split and spec-transport decision, and
each has exactly one job:

- **`docs/AUDIT_REMEDIATION_AND_RELEASE_PLAN.md` §8** states the chosen repository model and directs
  that this document, Stage 9, produce its implementation-ready detail. It is the origin of the
  decision, not a place that duplicates this document's design.
- **`docs/ARCHITECTURE.md` §3** states the target repository layout as architecture-level fact for
  readers who need the shape of the system, not the execution plan: `github.com/polytypo/polytypo`
  (canonical), `polytypo-js` (npm), `polytypo-python`, `polytypo-go`, `polytypo-ruby`, `polytypo-php`
  — the same naming this document and the audit plan use. §3.1 states, as decided architecture, that
  spec transport to every runtime repository is an automated, vendored, content-hash-verified
  snapshot — never a git submodule, never a per-ecosystem published spec package, never a
  consumer-time git dependency — and points here for the manifest format, hash algorithm, and
  dispatch/verification flow (§3–4), rather than restating them.
- **`docs/ROADMAP.md`** states milestones and, separately, the operator's genuinely open decisions.
  Its "Open decisions for the operator" list carries exactly two items that remain open — repository
  visibility (public from commit one vs. private until M4) and the first port (Python vs. Go) —
  because both require a judgment call this document does not make. Spec distribution, formerly a
  third open item, is not: `docs/ROADMAP.md` states the transport is the vendored, content-hash
  -verified snapshot this document specifies, consistently everywhere the topic is mentioned (its M1
  milestone note, its Phase B per-port checklist, and its open-decisions list all name the same
  design, not three independently worded descriptions of it). `docs/ROADMAP.md`'s M5 milestone uses
  this document's own tag convention, `spec-vX.Y.Z`, consistently with §4.
- **This document** is the sole source of implementation detail: the manifest schema and hash
  algorithm (§3), the dispatch and verification flow (§4), the conformance-evidence design (§5), the
  migration runbook (§2), and the hosting design (§7). None of the other three documents restate this
  detail; they reference it.

**Identifier discipline, consistent across all four documents:** a GitHub repository name
(`polytypo-js`), a registry package name (the npm package `polytypo`), and a canonical spec git tag
(`spec-vX.Y.Z`) are three distinct identifiers. No document conflates them — a version is never
written as `polytypo-js@<version>` (the repository name is not what a registry publishes), and a
spec version is never written with the `@` npm-style separator (`spec-vX.Y.Z` is this project's only
spec-tag syntax; `spec` is not itself a published package in any registry).

**Repo visibility and first-port choice remain open** in `docs/ROADMAP.md` and are unaffected by
anything in this document.
