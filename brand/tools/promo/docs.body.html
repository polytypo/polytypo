Reference

One function. No configuration, no globals, no I/O.

transform(input, options) takes a string and a locale and returns a string. It is pure: no filesystem, no network, no clock, no ambient config, no module-level state. Locale is required — an unknown locale throws rather than silently falling back to English.

What to pass in

A string that is prose from end to end goes to text; anything with tags goes to html; a Markdown file to markdown with its dialect; a YAML file to yaml with the keys of its prose fields. Choosing a mode covers what goes wrong with the wrong one, and invisible characters covers what the output contains that you cannot see.

Wiring it into a build step

transform() is a plain pure function, so it drops into whatever already touches your content at build time. Put it before your formatter: typography changes line lengths, since three dots become one character and no-break spaces are inserted, so a formatter that wraps prose should wrap the final text.

Why this and not a regex

Because the fifth port is where regex-based typography dies.

The spec is the product

Locale data, rule semantics and conformance fixtures live in one repository. An implementation is polytypo iff it passes the suite for the spec version it claims. Runtimes are replaceable; the spec is not.

No regex in the core

Go's RE2 has no lookbehind. A rule written as a clever regex in one language is a rule rewritten from scratch in the next. Rules are a single left-to-right scan over code points with explicit lookaround.

Idempotent by contract

transform(transform(x)) === transform(x), proven by property-based tests, not hoped for. Running it twice — in a CMS, in CI, in a build step — cannot corrupt text.

Every locale is cited

Duden, Imprimerie nationale, Kotus, Språkrådet, Chicago, Мильчин. A locale ships only as a triple: data, fixtures, citation. Disagreements are settled by source, not by preference.

{{Locale_count}} correct beats fifty guessed

The competing library with fifty locales guesses most of them. When the choice is "add a language" or "make an existing one provably correct", this project picks correctness.

Invisible characters, on purpose

U+00A0, U+202F and U+2011 are the whole point of the nbsp and hyphen rules. Every demo on this site reveals them with an underline — hover a highlighted character to see exactly what it is.

Before the text ever reaches a build step

Type it right in the first place: Ilya Birman's Typography Layout.

polytypo fixes text that has already been written. It is a repair pass — useful in a CMS, a build step, a content pipeline. But the best em dash is the one you typed on purpose, and for that there is a better tool than any library: a keyboard layout that puts real typographic characters under real keys.

Ilya Birman's Typography Layout is what we recommend, without reservation. It leaves your usual layout alone and adds the correct characters on the right-hand modifier: em dash, en dash, the quotation marks of many locales, the ellipsis, the no-break space, degrees, arrows, currency signs. You stop thinking about it within a week, and then you never type -- again.

Typing beats fixing

A rule engine has to infer intent from context. Your fingers already know it. Every character typed correctly is a character no heuristic has to guess at.

They compose

Use the layout while writing, run polytypo over the result. Text that is already correct passes through unchanged — that is what idempotency means in practice.

Where each one wins

The layout works where a person types. polytypo works where nobody is typing at all: imported catalogues, user submissions, migrated content, other people's Markdown.

Embedding the badge

What the badge needs, and what it does when it doesn't get it.

The span you paste is empty; the script fills it in. So if the script never runs — a Content Security Policy, a blocker, a loading strategy that doesn't fire — the span stays empty and nothing appears. The script cannot report that itself, since it never ran: what you have is the browser's own evidence, a CSP violation or a failed request, so check that badge.js was requested and executed before you look anywhere else. Every failure the script can see it writes to the console, prefixed polytypo badge:.

badge.js does no I/O at all. Every language and both themes are inlined in the file, so rendering is synchronous and works offline once the file is loaded. Serving it needs script-src https://polytypo.dev and nothing else: no connect-src, because nothing is fetched, and no img-src, because the mark is inline SVG. The badge styles itself with inline style attributes, so a policy that blocks inline styles leaves it unstyled.

async in the snippet is about your own page's load order and nothing else: once the file is evaluated, rendering is a synchronous read from that table. An unknown data-polytypo-lang or data-polytypo-theme renders English and the light theme rather than throwing, so a locale code where a language code belongs (de-CH instead of de) shows up as an English badge — with a console warning naming the attribute, the value, and the languages it accepts.

data-polytypo-lang and data-polytypo-theme are read once, when the script runs — on DOMContentLoaded, or immediately if the document is already parsed. Changing an attribute afterwards does nothing by itself: there is no MutationObserver and no matchMedia listener in the file. The script exports the hook for that: set the attribute, then call PolytypoBadge.render(el) to re-render that one badge, or PolytypoBadge.init() to re-render every badge on the page.

The same applies to a span that appears after the script has run — a client-side route change, a component mounted later. It is not picked up on its own; render it, or call init() again once it is in the document. A run of init() that finds no badge at all says so in the console rather than doing nothing quietly.
