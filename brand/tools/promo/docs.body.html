Reference

One function. No configuration, no globals, no I/O.

transform(input, options) takes a string and a locale and returns a string. It is pure: no filesystem, no network, no clock, no ambient config, no module-level state. Locale is required — an unknown locale throws rather than silently falling back to English.

Options

Option Type Default Notes
locale string — Required, no exceptions. Unknown locale throws POLYTYPO_UNKNOWN_LOCALE rather than falling back to English. Resolution (de-AT → de) follows spec/rules/locale-resolution.md. One call applies one locale, and the language is never detected: split a document that mixes languages and transform each part with its own locale.
mode "text" | "html" | "markdown" | "yaml" "text" Selects the adapter. text has no parser and no skip list: the whole string is prose to it. html parses with parse5 and takes a fragment as readily as a whole document; markdown parses with micromark. Both run the same rule pipeline only on prose text nodes, never inside tags, attributes, character references, code spans or code blocks. yaml uses no parser either — two of the five runtimes' YAML libraries cannot report the source offsets it would need — so it is a specified left-to-right scan, and it is the one mode that skips by default: it processes only the values of the keys you name in keys.
dialect "commonmark" | "mdx" — Required when mode is "markdown", with no default — omitting it throws POLYTYPO_INVALID_DIALECT. Dialect detection is forbidden by design: one <https://…> autolink is valid CommonMark and invalid MDX, so a heuristic would silently reclassify content. Ignored for the other three modes.
keys string[] — Required when mode is "yaml", with no default — omitting it throws POLYTYPO_INVALID_OPTION. Names the mapping keys whose values hold prose. There is no guess to make here: nothing in YAML's syntax separates a description: from a run:, and a mode that processed every string scalar would rewrite shell commands. Matching is exact, with no paths or globs, and the key itself is never processed. An empty list is legal and processes nothing. Ignored for the other three modes.
frontmatterKeys string[] — Optional, and only meaningful when mode is "markdown" (spec 1.7.0). Frontmatter is skipped whole by default, delimiters included, because it is a machine-read block — but on a site whose frontmatter carries the headline that leaves the most visible string on the page untouched. Naming keys processes their scalar values and nothing else in the block, with the same scan yaml mode uses, so the same constructs are refused: a single-quoted scalar containing '', which is how an apostrophe is written inside single quotes, comes back untouched. A TOML (+++) block is always skipped whole. The block is processed separately from the body, so an unbalanced quotation mark in title cannot pair with a mark in your first paragraph. Absent means the pre-1.7.0 behaviour; an empty list is legal and processes nothing.
narrowNbsp "narrow" | "nbsp" "narrow" "nbsp" makes the engine emit U+00A0 everywhere it would emit U+202F, the narrow no-break space many common faces do not carry (spec 1.3.0). It moves the rule's target rather than cleaning up afterwards, so the result is still a fixed point. Checked whether or not nbsp is enabled: the check belongs to the call.
rules Partial<Record<RuleId, boolean>> all on except ranges { dashes: false } switches a rule off. ranges is the one rule that is off by default: { ranges: true } switches it on. Disabling a rule removes it from the pipeline; it never reorders the rest. An unrecognised rule id throws POLYTYPO_UNKNOWN_RULE.

Error codes

All eight are part of the contract in every runtime; messages are English and are not.

Code Thrown when
POLYTYPO_UNKNOWN_LOCALE locale is missing or not in the spec's locale registry.
POLYTYPO_INVALID_MODE mode is set to something other than text, html, markdown or yaml.
POLYTYPO_INVALID_DIALECT mode: "markdown" without a dialect, or an unrecognised one.
POLYTYPO_INVALID_OPTION An option value outside its permitted set, where no more specific code applies — mode: "yaml" without keys, or a narrowNbsp that is neither "narrow" nor "nbsp". mode and dialect keep their own codes above.
POLYTYPO_UNKNOWN_RULE A key in rules that is not one of the {{rules_count}} rule ids.
POLYTYPO_MALFORMED_LOCALE_DATA Internal — a locale's data failed its own schema at load time.
POLYTYPO_RULE_CONTRACT Internal — a rule emitted an edit outside its contract (out of bounds, overlapping, wrong ruleId). Should never surface; if it does, it's a bug in this project, not your input.
POLYTYPO_MALFORMED_INPUT Reachable only when mode: "markdown" and dialect: "mdx" — MDX embeds JavaScript, so an unterminated JSX element or a broken {…} expression can fail to parse. html parsing is recovery-based and never throws this; plain CommonMark has no syntax errors at all. The underlying parser error is wrapped either way, so no dependency's error type reaches the public surface.

What to pass in

transform() sees only the string it is given. Rules read the characters on either side of what they change, and that reading stops at the ends of the string. Walk a component tree and transform each text node on its own, and every node boundary becomes one of those ends: Design and - the rest sent as two calls leave the hyphen alone. Send <strong>Design</strong> - the rest to html mode as one fragment and the dash is set, because html mode reads prose across inline elements.

text mode cannot tell code or markup from prose, so it typesets whatever is in the string. In code that means (c), (r), (tm) and x between numbers (symbols), spaces just inside (, [ and { (spaces), straight ' and " anywhere (quotes, apostrophe), and - between words (dashes). In French it also puts a no-break space before the ; that ends &amp;, and the reference is broken. Keep code out of a text call, or use the mode that knows where the code is: markdown skips code spans and blocks, html skips code, pre and character references. A string that can contain &amp; or &#160; is HTML, fragment or not.

In markdown mode those skipped regions are the dialect's own structural ones, not whatever looks like code to a reader. CommonMark calls an indented block code at four spaces; at two it is an ordinary paragraph, so a JSON sample indented by two spaces comes back with curly quotes — valid JSON in, invalid JSON out, and nothing in the return value says so. MDX has no indented code blocks at all, so there even four spaces is prose, and a brace inside it is a JSX expression: the same sample throws POLYTYPO_MALFORMED_INPUT instead. A fence or a code span is the one marker that means code in both dialects.

Frontmatter is the one skipped region you can open, key by key, with frontmatterKeys. Named that way round on purpose: the block holds slug, date and serviceSlug next to title and description, and only you know which is which. Measured on a 187-file site, the difference it makes is title: He said "hello" once → title: He said “hello” once while every other field keeps every byte.

What it inserts

Most of what transform() changes is visible: three dots become one ellipsis, a hyphen becomes a dash, straight quotes become the locale's own. Four insertions are not, and they are the ones to know about before the text reaches a renderer you don't control.

U+00A0, the no-break space, is the common one — French keeps it inside guillemets and before %, Russian binds it after № and inside и т. д., German holds S. 5 together. U+202F, the narrow no-break space, is emitted by fr alone, before ; ! and ?; fr-CA removes that space instead of narrowing it. U+2011, the non-breaking hyphen, comes from hyphen, whose lists are non-empty in ru alone. U+2060, the word joiner, wraps the dash of a bound range and appears only if you turn ranges on.

The last three are where font coverage stops being universal. A browser substitutes another face for a glyph its font lacks, at a slightly different width; a PDF renderer with one embedded font can drop the character instead. Check the font on that path before you ship. rules: { hyphen: false } turns off the only rule that emits U+2011, and ranges is off by default, so U+2060 appears only where you asked for it. The joiner is what keeps a range from breaking across lines, which both Мильчин and Chicago require, so stripping it afterwards costs exactly that.

Wiring it into a build step

transform() is a plain pure function, so it drops into whatever already touches your content at build time. Put it before your formatter: typography changes line lengths, since three dots become one character and no-break spaces are inserted, so a formatter that wraps prose should wrap the final text.

Why this and not a regex

Because the fifth port is where regex-based typography dies.

The spec is the product

Locale data, rule semantics and conformance fixtures live in one repository. An implementation is polytypo iff it passes the suite for the spec version it claims. Runtimes are replaceable; the spec is not.

No regex in the core

Go's RE2 has no lookbehind. A rule written as a clever regex in one language is a rule rewritten from scratch in the next. Rules are a single left-to-right scan over code points with explicit lookaround.

Idempotent by contract

transform(transform(x)) === transform(x), proven by property-based tests, not hoped for. Running it twice — in a CMS, in CI, in a build step — cannot corrupt text.

Every locale is cited

Duden, Imprimerie nationale, Kotus, Språkrådet, Chicago, Мильчин. A locale ships only as a triple: data, fixtures, citation. Disagreements are settled by source, not by preference.

{{Locale_count}} correct beats fifty guessed

The competing library with fifty locales guesses most of them. When the choice is "add a language" or "make an existing one provably correct", this project picks correctness.

Invisible characters, on purpose

U+00A0, U+202F and U+2011 are the whole point of the nbsp and hyphen rules. Every demo on this site reveals them with an underline — hover a highlighted character to see exactly what it is.

Before the text ever reaches a build step

Type it right in the first place: Ilya Birman's Typography Layout.

polytypo fixes text that has already been written. It is a repair pass — useful in a CMS, a build step, a content pipeline. But the best em dash is the one you typed on purpose, and for that there is a better tool than any library: a keyboard layout that puts real typographic characters under real keys.

Ilya Birman's Typography Layout is what we recommend, without reservation, for macOS and Windows. It leaves your usual layout alone and adds the correct characters on the right-hand modifier: em dash, en dash, the quotation marks of several languages, the ellipsis, the no-break space, degrees, arrows, currency signs. You stop thinking about it within a week, and then you never type -- again.

Typing beats fixing

A rule engine has to infer intent from context. Your fingers already know it. Every character typed correctly is a character no heuristic has to guess at.

They compose

Use the layout while writing, run polytypo over the result. Text that is already correct passes through unchanged — that is what idempotency means in practice.

Where each one wins

The layout works where a person types. polytypo works where nobody is typing at all: imported catalogues, user submissions, migrated content, other people's Markdown.

Embedding the badge

What the badge needs, and what it does when it doesn't get it.

The span you paste is empty; the script fills it in. So if the script never runs — a Content Security Policy, a blocker, a loading strategy that doesn't fire — the span stays empty and nothing appears. The script cannot report that itself, since it never ran: what you have is the browser's own evidence, a CSP violation or a failed request, so check that badge.js was requested and executed before you look anywhere else. Every failure the script can see it writes to the console, prefixed polytypo badge:.

badge.js does no I/O at all. Every language and both themes are inlined in the file, so rendering is synchronous and works offline once the file is loaded. Serving it needs script-src https://polytypo.dev and nothing else: no connect-src, because nothing is fetched, and no img-src, because the mark is inline SVG. The badge styles itself with inline style attributes, so a policy that blocks inline styles leaves it unstyled.

async in the snippet is about your own page's load order and nothing else: once the file is evaluated, rendering is a synchronous read from that table. An unknown data-polytypo-lang or data-polytypo-theme renders English and the light theme rather than throwing, so a locale code where a language code belongs (de-CH instead of de) shows up as an English badge — with a console warning naming the attribute, the value, and the seven languages it accepts.

data-polytypo-lang and data-polytypo-theme are read once, when the script runs — on DOMContentLoaded, or immediately if the document is already parsed. Changing an attribute afterwards does nothing by itself: there is no MutationObserver and no matchMedia listener in the file. The script exports the hook for that: set the attribute, then call PolytypoBadge.render(el) to re-render that one badge, or PolytypoBadge.init() to re-render every badge on the page.

The same applies to a span that appears after the script has run — a client-side route change, a component mounted later. It is not picked up on its own; render it, or call init() again once it is in the document. A run of init() that finds no badge at all says so in the console rather than doing nothing quietly.
